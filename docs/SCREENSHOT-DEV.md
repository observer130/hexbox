# 截屏覆盖层：开发文档

> 目标：在游戏画面内**直接**绘制数据（英雄卡片下方显示胜率），
> 替代侧边的独立悬浮窗。
>
> **实现状态（2026-09-28）**：S1 与 S2 均已实现并离线全绿，
> **待真机复验**（见 §四 与 [SESSION-NOTES.md](SESSION-NOTES.md)）。
> 本文记录技术事实与踩过的坑；最近一轮的验收 bug 记录在 SESSION-NOTES。
>
> 合规：截屏只读取屏幕像素，**不注入、不读内存、不解析封包**。
> 见 [AGENTS.md](../AGENTS.md) —— 这是明确许可的做法。
>
> ➡️ **局内（对局中）的海克斯面板识别是另一条链路**，见
> [AUGMENT-PANEL.md](AUGMENT-PANEL.md)：那一侧不预测刷新时间，
> 只识别"面板在/不在"的开/关边沿，门控纯函数在
> `packages/vision/src/augment-panel.ts`。

## 一、总体结构

### 已验证的技术事实

| 项 | 结果 | 验证方式 |
|---|---|---|
| 能否截屏游戏窗口 | ✅ | `desktopCapturer` 枚举到 `League of Legends` 窗口 |
| 截屏分辨率 | ✅ 4587×1920 | 全分辨率，英雄头像清晰可辨 |
| 与显示器的关系 | **2.0x**（显示器 2294×960 @1.5 DPI 缩放）| 实测换算 |
| 是否触碰硬约束 | ✅ 不触碰 | 纯像素读取 |

> ⚠️ 截屏尺寸 = 显示器逻辑尺寸 × **2**，且游戏窗口比显示器小。
> **不能**把截屏坐标直接当屏幕坐标用 —— 这是最容易出错的地方，
> 必须先做 §3.1 的两层换算。

### 数据流

```
截屏(desktopCapturer) → 定位卡片 → 识别英雄 → 查本地数据 → 绘制覆盖层
        每 ~1s 一次        纯函数      纯函数      只读 data/
```

### 布局示意

```
┌─ 游戏窗口（不可控）───────────────────────┐
│                                          │
│   [英雄卡片]  [英雄卡片]  [英雄卡片]      │  ← 截屏读取
│      ↓ 定位 + 识别                        │
│   ┌──────┐   ┌──────┐   ┌──────┐         │
│   │57.2% │   │51.4% │   │48.9% │         │  ← 覆盖层绘制
│   └──────┘   └──────┘   └──────┘         │
│                                          │
└──────────────────────────────────────────┘
        ↑ Electron 全屏透明窗口（click-through）
```

## 三、关键技术点

### 3.1 坐标换算（必须先做对）

实测：截屏尺寸 = 显示器逻辑尺寸 × **2.0**
（截屏 4587×1920，显示器 2294×960 @1.5 DPI）。

且**游戏窗口可能小于显示器**，因此有两层换算：

```
截屏像素坐标
   │  ÷ captureScale（截屏尺寸 ÷ 窗口物理尺寸，运行时自校准）
   ▼
窗口物理像素坐标
   │  × 窗口屏幕位置；÷ display.scaleFactor（物理 → 逻辑 DIP）
   ▼
屏幕逻辑坐标 → 覆盖层窗口坐标
```

**已确认的坐标系事实**（2026-09-27 实测）：
- GetWindowRect 返回**物理像素**（Electron 主进程是 Per-Monitor-V2 感知）；
- Electron `screen`/`display` 用**逻辑 DIP**；
- desktopCapturer 缩略图尺寸 = 物理像素 × 内部缩放（不可假设）。

因此**不要假设固定倍率**：`captureScale` 用「窗口物理矩形 ÷ 截屏尺寸」
运行时求出（`vision/win-geometry.ts`），拿不到窗口矩形时才按 1.0 兜底。

**建议统一用 0..1 归一化坐标做中间表示**，与分辨率解耦。

### 3.2 卡片定位

不要硬编码像素。用**结构性特征**：

1. **粗定位**：卡片区通常在屏幕中部，占宽度约 40~90%（用比例缩小搜索范围）
2. **精定位**：卡片有**金色边框**，可在候选区域内做颜色掩码，
   对列方向投影找等距竖线 → 推断卡片左右边界
3. **验证**：找到的卡片数应为 3（或 5），间距大致相等；
   不符合则判定失败、**不绘制**

> 用「等距」这一强约束做校验，可以过滤掉大部分误检。

### 3.3 英雄识别（两阶段,真机校准定稿）

**阶段 1 —— 悬停卡片名字区 OCR（主通道）**：
卡片区下部有印刷体英雄名（白字,Microsoft YaHei,与游戏内字体同源）。
`vision/ocr.ts`：名字带二值化 → 裁剪文字包围盒 → 统一网格拉伸 →
与名字指纹库（`pnpm templates` 构建,`scripts/render-name-fingerprints.ps1`
渲染 **245 条**名字 —— 173 真实英雄 + 72 条同一英雄的变体条目）做 Jaccard 匹配。
离线回放真机截图：2/2 正确（0.608/0.552,错误名 < 0.45）。

**阶段 2 —— 确认态顶栏逐格匹配（2026-09-28 重做）**：
英雄锁定后,顶部「可用」栏列出**未选的备选英雄**（方头像,
官方 champion-icons 同源）。此阶段给**每个有头像的格子**各显示一个胜率标签：

- 几何：`confirmed.ts` TOP_BAR_ROW（第 1 格 x=659/2400,步进 110/2400,
  共 10 格,归一化后跨分辨率稳定 —— 两张真机截图交叉验证一致）
- 占用检测：内部 12% 内缩 16×16 灰度 std（亮头像 60+ / 暗头像低至 42 /
  空格 <9,阈值 0.12 —— 暗色头像曾被 0.18 阈值误判为空格,真实 bug）
- 识别：**整个槽位盒**提取 24×24 灰度做 NCC,阈值 0.80/0.05
  （同源匹配得分 0.93+;⚠️ 内缩提取会把得分压到 0.79,是上一轮
  「确认态无显示」的根因之一,勿改回）
- 截屏形态：槽位几何按**窗口**归一化存储,识别前经
  `win-geometry.windowRectToCapture` 变换到截屏空间
  （window 形态恒等,display 形态平移缩放）

> ⚠️ **头像模板不能用于悬停卡片立绘**：卡片立绘是游戏内实时渲染,
> 与静态头像构图差异大,24×24 灰度模板的正确答案得分仅 ~0.53,
> 而错误冠军可达 0.88 —— 两次真机验证,假阳性系统性存在。
> 立绘识别只用阶段 1 的名字 OCR;方头像匹配只用于阶段 2。
>
> ⚠️ `data/templates.json` 中的 60000+ 变体 ID（CDragon 静态占位）
> 与真英雄同名同图,匹配命中后 join 不到数据 —— 加载时已排除。

### 3.4 绘制

复用现有窗口机制（侧边栏已验证）：

```js
transparent: true, frame: false,
alwaysOnTop: 'screen-saver',
focusable: false,            // 不抢焦点
skipTaskbar: true
win.setIgnoreMouseEvents(true, { forward: true })  // 鼠标穿透
```

区别：窗口变为**全屏透明**，内容按检测到的卡片坐标绝对定位。

## 六、验收标准

**每条都必须满足，否则不算完成**：

1. 分辨率改变（如窗口化 / 不同缩放）后仍能正确定位
2. 识别不确定时**不绘制**，而不是画错的数字
3. 覆盖层不影响游戏操作（键盘、鼠标、焦点）
4. 纯函数部分有单测；标注图可人工核对
5. 三闸门（test / typecheck / build）保持绿

## 八、标签记忆的两个真机 bug（2026-10-11）

### 8.1 「第四个悬浮标签」（幽灵标签）

用户打包版日志（`%LOCALAPPDATA%\hexbox\logs\overlay.log` L34 → L40）：

```
L34 推送 active=true labels=1 … 第一阶段: 卡片 2 张 → 出标签 1 个 … 标签0@(1160,621)
L40 推送 active=true labels=4 … 第一阶段: 卡片 3 张 → 出标签 3 个 … 标签0@(757,614)
L41~L78 draw labels=4（约 20~25 秒）→ L79 才回到 3
```

`label-memory.ts` 的"按位置记忆"（容差 24 DIP、TTL 6 轮、只比 x/y）在某一轮
`detectCards` **误检**（候选行被当成 2 张卡、名字只低置信命中）产出标签 @(1160,621)
之后，下一轮正确检出 3 张卡时三个新标签与它**两两都差 >24 DIP** →
位置规则认不出"同一个元素被重认"，于是**原样保留** → 屏幕上是 4 个。

**修法**：记忆里记"本块 UI 见过的**最大元素数**" `capacity`
（`reset()` 清 0、每轮用本轮输入条目数取 max），合并输出时
`if (out.length >= capacity) break`。两条语义都保住：

- 3 张卡某轮只检出 2 张 → 容量仍是 3 → 仍能补齐第 3 个（本模块最初的目的）；
- 误检成 2 张后再检出 3 张 → 容量升到 3 且被新标签占满 → 幽灵**永远进不来**。

### 8.2 二阶段的卡片标签：换阶段要按**实际阶段**判，`pickState` 只读一次

真机日志 L86：`推送 active=true labels=3 … 第二阶段(locked): 顶栏占用 2 格, 识别成功 0 格`
—— 二阶段本轮产出 0 个，却还推 3 个**卡片**标签（靠 TTL 挂着）。

两个成因，各修一处（`apps/overlay/src/main/vision-loop.ts`）：

1. `tick()` 在截屏**之前**读一次 `pickState` 用于清记忆，`runVisionRound()`
   内部又读一次用于阶段判定 —— 中间隔着 1~2 秒的截屏 await，LCU 每 2 秒轮询
   足以把 picking 翻成 locked（"本轮报 second 阶段却仍推卡片标签"）。
   → **每 tick 只读一次**并作为参数传进 `runVisionRound(deps, pickState)`。
2. `isPhase2` 的另一半是"顶栏占用 > 0"，而那条路径下 LCU 的 `pickState` 可能是
   `unknown`/`picking`（**永远不变**）→ 只看 `pickState` 的换阶段判据永不触发。
   → `runVisionRound()` 回报**实际阶段**（`stage: 'cards' | 'topbar' | null`），
   `tick()` 在阶段变化时 `memory.reset()`（`pickState` 变化那条保留作补充）。

## 九、选人第一阶段「候选卡」几何标定（2026-10-12，v0.1.1）

### 9.1 旧 `detectCards` 在选人帧上为什么不能用

真机日志（打包版 0.1.0）里同一套「选择你的英雄」界面：

```
第一阶段(picking)但未检出卡片: 等宽候选桶均未通过间隙/纵横比校验（共 6 个候选桶）
第一阶段(picking): 卡片 3 张 → 出标签 2 个 [得分/分差 0.52/0.05 拒绝:分数不够(墨迹6%) …]
第二阶段(picking): 顶栏占用 3 格 …            ← 修前：队友把顶栏填满就翻阶段（见 §八 8.2）
```

**根因（离线复现，已证实）**：`grid.ts` 的 `cardsFromBands` 按**宽度 ±2% 聚桶**，
而选人卡的左右边框在真机帧上会与相邻装饰线合并成**不同厚度**的带
（左边框 26px、右边框 36px）→ 同一张卡量出 473px / 462px（差 2.3%）→ 落进两个桶
→ 每桶只剩 1 对 → `pairs.length >= 2` 过滤掉 → **0 张**；换个帧量出 472/467
（差 1.1%）→ 成 2 张。**0 与 2 张之间只差 1.2% 的测量噪声。**

它还会在**第二阶段**（锁定后的大立绘）帧上给出两个位置完全错误的矩形
（`x≈0.3191/0.5432, w≈0.2025, h≈0.61` —— 那是美术图圆环里的两块区域）。

### 9.2 真机标定出来的布局

布局是**居中、等宽、等间距**的一行卡片，张数 **2 或 3**（两种都真实出现过）。
证据来自打包版日志里第一张卡的标签坐标（标签与卡片同宽，且
`x` 是屏幕 DIP，减去窗口原点 347 即窗口内坐标）：

| 张数 | 日志 | 窗口归一化 |
|---|---|---|
| 3 | `标签0@(760,…) w=233.93`（窗口 1600×900@347,6） | 卡宽 0.14621、首卡 x 0.25813 |
| 2 | `标签0@(894,…) w=233.46` | 卡宽 0.14591、首卡 x 0.34188 |

再与真机帧的边框带外缘（3413×1920：卡 1166..1663 / 1741..2240，纵向 477..1277；
2393×1347：817..1166 / 1221..1572）交叉验证，得到一套常数
（`vision/champ-select-cards.ts` 的 `CHAMP_SELECT_CARD_LAYOUT`）：


### 9.3 判据：边框能用，"内部暗"不能用

逐帧量测（正样本 6 帧 / 阴性 13 帧）：

| 判据 | 正样本（真候选卡） | 阴性（第二阶段大立绘 / 局内海克斯面板） |
|---|---|---|
| 四条边框"亮线 vs 卡外背景"亮度差 | 最小单边 **16.2**，四边和 **156~231** | 单边 ≤ 8；局内面板只有一条边亮（另三边 ≈0） |
| 卡内平均亮度（"内部暗"） | 48.7~73.3（**立绘可以很亮**） | 39.7~117.9（与正样本**重叠**） |

所以检出器只用**边框判据** + 严格按标定布局取位：

1. 按布局生成 3 张、2 张两组期望矩形（依次尝试，全有或全无）；
2. 每条边在 ±0.5% 窗口宽内找**象牙白高光峰**（= 这条边确实存在），
   再从峰往卡外退到"亮度回到 背景 + 0.35×峰值"的那一点 = **可见外缘**
   （真机剖面：`…1160:17 1161:14 1162:10 1164:23 1166:49 1170:70 1175:73 1179:164…`
   —— 只取峰值会让每条边内缩 ~13px，四边加起来整框小 5%，**名字带下缘切到卡片底边、
   OCR 得分掉一半**：实测 0.15~0.25 时识别 4~7/12，0.30~0.50 时 10/12）；
3. 四边都 ≥14、四边和 ≥90 才算这张卡成立；任意一张不成立 → 整个假设作废
   （**绝不给部分结果**）。

### 9.5 标签位置与英雄的对应关系（怎么证明）

同一个矩形同时决定**标签位置**和**名字带裁剪**，所以"标签画在哪个格子"与
"这个标签是哪个英雄"在代码里是同一件事（`vision-loop.ts` 第一阶段）：
矩形 → `NAME_STRIP` 裁名字带 → `extractNameStrip` + `matchNameCareful` 得到英雄 →
`cardLabelFor(同一个矩形, …)` 画标签。名字带宽度是卡宽的 0.78 且居中，
两侧各留 0.11 卡宽（> 卡片间隙 0.0227 窗口宽），**不可能读到隔壁卡的名字**。

证据（`--ocr`）：6 帧 12 张卡里 10 张的 OCR 名字与目视名字一致
（`痛苦之拥`/`风暴之怒`、`纳祖芒荣耀`/`殇之木乃伊`、`傲之追猎者`/`狂野女猎手`）。
2 张没认出来的都是同一张卡（`real/verify1.png`/`shot1.png` 的 `傲之追猎者`）——
名字指纹匹配的得分就在阈值（0.4）附近，几何本身没问题：同一张卡用**目视真值矩形**
反而也是 8/12。失败方向是"不画"，不是"画错英雄"。

### 9.6 开关与残余风险

| 变量 | 含义 |
|---|---|
| `HEXBOX_CHAMP_SELECT_CARDS=geometry` | **默认**：上面的标定几何 |
| `HEXBOX_CHAMP_SELECT_CARDS=legacy` | 旧的自由搜索 `detectCards`（对照用；真机不稳） |
| `HEXBOX_CHAMP_SELECT_CARDS=off` | 一张都不画（只出顶栏标签） |

残余风险（未验证项）：**没有 3 张卡的真机帧**可离线复验 —— 3 张排布只有日志
坐标 + 居中推算两条证据；若真机上 3 张卡的首卡 x 与 0.2581 差得多，检出器会
直接判"未检出"（宁可不画），届时用 `--annotate` 抓一张 3 张卡的帧即可复核。
另外超宽屏（非 16:9）下客户端是否仍按同一套归一化布局渲染，未验证。
