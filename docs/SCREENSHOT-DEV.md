# 截屏覆盖层：开发文档

> 目标：在游戏画面内**直接**绘制数据（英雄卡片下方显示胜率），
> 替代侧边的独立悬浮窗。
>
> 合规：截屏只读取屏幕像素，**不注入、不读内存、不解析封包**。
> 见 [AGENTS.md](../AGENTS.md) —— 这是明确许可的做法。

## 一、总体结构

### 已验证的技术事实

| 项 | 结果 | 验证方式 |
|---|---|---|
| 能否截屏游戏窗口 | ✅ | `desktopCapturer` 枚举到 `League of Legends` 窗口 |
| 截屏分辨率 | ✅ 4587×1920 | 全分辨率，英雄头像清晰可辨 |
| 与显示器的关系 | **2.0x**（显示器 2294×960 @1.5 DPI 缩放）| 实测换算 |
| 是否触碰硬约束 | ✅ 不触碰 | 纯像素读取 |

> ⚠️ 截屏尺寸 = 显示器逻辑尺寸 × **2**，且游戏窗口比显示器小。
> **不能**把截屏坐标直接当屏幕坐标用 —— 这是最容易出错的地方，
> 必须先做 §3.1 的两层换算。

### 数据流

```
截屏(desktopCapturer) → 定位卡片 → 识别英雄 → 查本地数据 → 绘制覆盖层
        每 ~1s 一次        纯函数      纯函数      只读 data/
```

### 布局示意

```
┌─ 游戏窗口（不可控）───────────────────────┐
│                                          │
│   [英雄卡片]  [英雄卡片]  [英雄卡片]      │  ← 截屏读取
│      ↓ 定位 + 识别                        │
│   ┌──────┐   ┌──────┐   ┌──────┐         │
│   │57.2% │   │51.4% │   │48.9% │         │  ← 覆盖层绘制
│   └──────┘   └──────┘   └──────┘         │
│                                          │
└──────────────────────────────────────────┘
        ↑ Electron 全屏透明窗口（click-through）
```

## 二、模块划分

新增包 `packages/vision`（纯函数，可单测）：

| 文件 | 职责 | 是否纯函数 |
|---|---|---|
| `geometry.ts` | 坐标换算（截屏↔屏幕）、矩形运算 | ✅ |
| `grid.ts` | 从截屏推断卡片网格布局 | ✅（输入像素，输出矩形）|
| `match.ts` | 头像模板匹配打分 | ✅ |
| `types.ts` | `Rect` / `CardSlot` / `MatchResult` | — |

`apps/overlay` 增加：

| 文件 | 职责 |
|---|---|
| `src/main/capture.ts` | 截屏（Electron API，非纯函数）|
| `src/main/vision-loop.ts` | 定时截屏 → 调 vision → 推送结果 |
| `src/renderer/overlay-canvas.ts` | 按坐标把文本画到对应位置 |

> **为什么放 core/vision 而不是主进程**：主进程需要 Electron + 真实桌面，
> CI 跑不起来。只有纯函数才能被测试覆盖 —— 这是本项目一贯的做法
> （见 `core/src/overlay-view.ts` 的先例）。

## 三、关键技术点

### 3.1 坐标换算（必须先做对）

实测：截屏尺寸 = 显示器逻辑尺寸 × **2.0**
（截屏 4587×1920，显示器 2294×960 @1.5 DPI）。

且**游戏窗口可能小于显示器**，因此有两层换算：

```
截屏像素坐标
   │  ÷ captureScale（截屏尺寸 ÷ 窗口物理尺寸）
   ▼
窗口内逻辑坐标（0..1 归一化更稳）
   │  × 窗口屏幕尺寸 + 窗口屏幕位置
   ▼
屏幕绝对坐标 → 覆盖层窗口坐标
```

**建议统一用 0..1 归一化坐标做中间表示**，与分辨率解耦。

### 3.2 卡片定位

不要硬编码像素。用**结构性特征**：

1. **粗定位**：卡片区通常在屏幕中部，占宽度约 40~90%（用比例缩小搜索范围）
2. **精定位**：卡片有**金色边框**，可在候选区域内做颜色掩码，
   对列方向投影找等距竖线 → 推断卡片左右边界
3. **验证**：找到的卡片数应为 3（或 5），间距大致相等；
   不符合则判定失败、**不绘制**

> 用「等距」这一强约束做校验，可以过滤掉大部分误检。

### 3.3 英雄识别

**用头像模板匹配，不用 OCR**（卡片上的英雄名是美术字体，中文 OCR 不可靠）。

- 本地已有 245 个英雄头像（`dataset.json` 的 `champions[].iconPath`）
- 卡片上是固定尺寸的方形头像，缩放到统一尺寸后与本地头像比相似度
- 相似度低于阈值 → **不显示**，绝不猜

**预处理建议**：转灰度 + 缩放到固定尺寸（如 32×32）+ 归一化，
再用简单的 L1/L2 距离或归一化互相关。

### 3.4 绘制

复用现有窗口机制（侧边栏已验证）：

```js
transparent: true, frame: false,
alwaysOnTop: 'screen-saver',
focusable: false,            // 不抢焦点
skipTaskbar: true
win.setIgnoreMouseEvents(true, { forward: true })  // 鼠标穿透
```

区别：窗口变为**全屏透明**，内容按检测到的卡片坐标绝对定位。

## 五、风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 分辨率 / UI 缩放变化 | 定位失效 | 归一化坐标 + 比例定位，不硬编码 |
| 游戏 UI 改版 | 定位失效 | 检测失败即**静默不绘制**，绝不错标 |
| 全屏覆盖层挡操作 | 影响游戏 | `focusable:false` + 鼠标穿透（已验证）|
| 截屏性能 | 掉帧 | 仅选人阶段截屏，约 1s 一次 |
| 头像匹配误判 | 显示错误胜率 | 阈值 + 多候选校验，宁可漏不可错 |
| 游戏更新导致布局变化 | 需重新适配 | 提供调试命令输出标注图，便于快速定位 |

## 六、验收标准

**每条都必须满足，否则不算完成**：

1. 分辨率改变（如窗口化 / 不同缩放）后仍能正确定位
2. 识别不确定时**不绘制**，而不是画错的数字
3. 覆盖层不影响游戏操作（键盘、鼠标、焦点）
4. 纯函数部分有单测；标注图可人工核对
5. 三闸门（test / typecheck / build）保持绿

## 七、开发环境限制（重要）

**我（AI）无法真机验证**：需要管理员权限 + 真实桌面 + 一局真实对局。

因此流程必须是：

1. 我实现 + 单测 + 提供**调试命令**
2. 你在选人阶段运行调试命令，把**标注图**发我
3. 我根据标注图调整算法
4. 重复 2-3 直到定位稳定，再做覆盖层绘制

> 这个反馈回路是必须的 —— 盲写算法只会让你反复试错。
