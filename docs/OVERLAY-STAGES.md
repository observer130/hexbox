# 悬浮窗分阶段设计：调研依据与已确认事实

> 本文记录**为什么**悬浮窗按现在这样分阶段设计，以及调研中查证到的事实。
> 目的是避免后人（或 AI）重走弯路。
>
> 实现状态见 [apps/overlay/README.md](../apps/overlay/README.md)。

## 一、核心原则

**不同阶段显示不同内容。** 玩家在各阶段做的决策不同，
显示与该阶段无关的数据只会干扰。

| 阶段 | 玩家在做什么决策 | 该显示什么 |
|---|---|---|
| 英雄选择 | 选**英雄** | 英雄的海斗胜率 |
| 对局中 | 选**海克斯** | **以该英雄为准**的海克斯强度 |
| 对局中 | 出装 | 出装建议（→ 配装方案，不在悬浮窗） |

## 二、调研对象

### 虎牙海斗助手（`gametool.huya.com/lolhex`）

| 阶段 | 它提供什么 |
|---|---|
| 英雄选择 | 所选英雄的海斗胜率；强度评级（T1–T5）；热门玩法 |
| 海克斯选择 | **以英雄为准**的海克斯强度（S/A/B/C）；联动与冲突提醒 |
| 局内 | 按英雄与当前构筑整理出装顺序 |

### 官方 101 数据站的海斗专属英雄页

`https://101.qq.com/#/hero-detail?heroId=<id>&mode=hextech&lane=<lane>`

四个区块：**符文**（海克斯强度 + 登场率）/ **技能加点** / **出装** / **最佳拍档**。

## 三、曾犯过的错（记录以免重犯）

| # | 错误 | 纠正 |
|---|---|---|
| 1 | **选人阶段显示海克斯胜率** | 选人时玩家在选英雄，海克斯还没出现 —— 臆想的需求 |
| 2 | **海克斯榜用全局胜率** | 同类工具用「以该英雄为准」的强度 |
| 3 | 曾判定「海斗专属出装无数据」 | **错**：只查了 `fuwen_aram_*`（全局榜），漏了单英雄接口 |
| 4 | 曾判定「官方海斗页不显示出装」 | **错**：等待时间不足漏抓请求，加大等待后确认会请求 |
| 5 | **擅自扩大数据用途** | 用了官方页面不展示的 `itemover_rec` 当「六神装」，用户找不到出处 |

> 教训：**先验证数据是否真的存在，再决定做什么**；
> 且**只用官方展示过的字段**，不自行发明口径。

## 四、数据源（实测验证）

**同一个接口提供全部单英雄数据**：

```
https://mlol.qt.qq.com/go/battle_info/odp_proxy/fuwen_hero_rank?championid=<英雄ID>
```

> ⚠️ 这是 `fuwen_hero_rank`（单英雄），**不是** `fuwen_aram_hero_rank_v2`（全局榜）。
> 两者是完全不同的接口，混淆会导致误判「无数据」。

| 字段 | 含义 | 格式 |
|---|---|---|
| `augment_json_irank` | 该英雄的海克斯强度 | `排名\|英雄ID\|海克斯ID\|等级\|登场率\|强度`，**带稀有度分组**，`#` 分隔 |
| `itemone_json` | 出门装 / 其余成装（单件） | JSON，**万分比** |
| `itemshoes` | 鞋（本工具未采用，见下） | `itemId$登场率$胜率`，比率 |
| `itemcore_json` | 优先成装（三件套） | JSON，`&` 分隔多件，**万分比** |
| `itemout` | 出门组合 | `itemIds$登场率$胜率`，比率 |
| `championid_json` | 最佳拍档 | `英雄ID\|胜率\|登场率\|排名` |
| `skill_json` | 技能加点 | JSON，`sk_s`/`sk_w` 是**原始计数** |
| `dtstatdate` | 统计日期 | `20260925` |

> ⚠️ **`augment_json_irank` 是「以该英雄为准」的池，不是图鉴全量**（2026-10-05 实测）：
> 每个英雄 95~162 条（中位数 126），约图鉴 248 的 43%~57%。这不是抓漏/截断 ——
> 原始块数 == 解析条数、`255` 组 == 三个品质组的并集、173 个英雄的并集 == 全局榜 211 条。
> 同接口的 `augment_json`（每品质前 10、5 列无强度）更少，**刻意不采集**。
> 覆盖率实测与纪律见 [AUGMENT-PANEL.md](AUGMENT-PANEL.md) §十二。

### 解析时必须注意的三点

1. **`augment_json_irank` 带稀有度分组**：组头形如 `255:1|…`，
   同组后续条目省略组名。按 `#` 直切会得到 249 条（含跨组重复），
   正确应为 126 条（`255` = 全部品质组）。
2. **单位不统一**：`itemone_json`/`itemcore_json` 是**万分比**（6033 = 60.33%），
   而 `itemshoes`/`itemout` 是**比率**（0.5618）。混用会得到 5618% 这种荒谬数字。
3. **`sk_s`/`sk_w` 是原始计数**（1312 / 5578），不是比率。
   登场率 = `sk_s / sk_w`。

### 关键陷阱与对策

| 陷阱 | 后果 | 对策 |
|---|---|---|
| 上游**不按登场率排序** | 取到的「第一名」是错的 | 自己按 `pickRate` 降序排 |
| 「其余成装」与「出门装」同源 | 以为缺字段 | 页面把 `itemone_json` 展示了两次（前 5 / 全部 20）|
| `associatedMaps` 填错 | 配装方案静默不出现 | 海斗用 **12** |

## 五、已确认的决策

| 项 | 决定 | 理由 |
|---|---|---|
| 选人阶段 | **仅显示胜率** | Tier 不做（见下） |
| Tier 强度分级 | **不做** | 官方页的 T0 不在任何接口返回里，是前端计算；不自行编公式 |
| 海克斯强度 | 放**局内**，标为「以该英雄为准」 | 与同类工具一致 |
| 最佳拍档 | 不显示 | 用户明确要求 |
| 避坑海克斯 | 不做 | 同上 |
| 出装 | **写入配装方案**，不放悬浮窗 | 见 [build-slots.md](build-slots.md) |
| 鞋栏 | **不生成** | 一行只有一件装备，游戏内既不好看也无信息量 |
| 预抓范围 | 245 条英雄条目全抓（**173 真实英雄 + 72 条同一英雄的变体条目**）| 实测 173 个英雄有官方统计；72 条变体条目没有独立统计 |

### 关于 Tier 的查证记录

官方海斗英雄页顶部渲染 `T0.png`，但实测**任何接口都不返回该字段**：

| 候选来源 | 亚索结果 | 与页头 T0 一致 |
|---|---|---|
| `lol_101strategy?lane=ALL` | T3 / 50.56% | ❌（峡谷口径）|
| `lol_101strategy_newlane`（分路） | T3 / T3 / T4 | ❌ |
| `fuwen_aram_hero_rank_v2` | #1 / 57.23% | 数值一致但**无 tier 字段** |
| `fuwen_hero_rank?championid=` | 无 tier 字段 | ❌ |

结论：T0 是**前端计算**的，官方未公开口径。
**不自行编造公式** —— 一律不显示 Tier（胜率本身已是官方直出、可核对）。

## 六、当前实现对应关系

| 设计要点 | 实现位置 |
|---|---|
| 分阶段视图（胜率/强度/出装） | `packages/core/src/overlay-view.ts` |
| 单英雄详情拉取与解析 | `packages/provider-tencent/src/index.ts` |
| 落盘 `builds.json` | `packages/data-store` + `packages/data-cli` |
| 悬浮窗分阶段渲染 | `apps/overlay/src/renderer/renderer.ts` |
| 出装 → 配装方案 | `packages/core/src/itemset.ts` |

### 纯函数放 core 的原因

悬浮窗需要**管理员权限 + 真实桌面会话**，CI 根本跑不起来。
只有把逻辑抽成纯函数（`overlay-view.ts` / `itemset.ts`），
才能被单元测试覆盖。
