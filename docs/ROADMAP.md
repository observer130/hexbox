### 2.4 LCU 与硬约束的落地

- `isBrawlSession()` 用官方常量判定（`gameMode === 'BRAWL'` 或 `queueId === 2300`）。
- 凭证获取：进程命令行（需管理员）→ lockfile 递归查找 → 监听端口探测。
- 国服实测坑已记录：`LeagueClient\lockfile` 为 0 字节，不可依赖。
- 硬约束真实成立：全程只读进程**元数据**与**窗口几何**（`GetWindowRect`），
  未打开游戏进程句柄、未读内存、未注入、未解析封包。

## 三、本轮修复的缺陷

### 3.1 时间炸弹测试（已修复）

`packages/provider-tencent/src/index.test.ts` 中的
「HTTP 失败后回退到更早日期」用例，把 T-1 写死为 `20260924`。

但实现里的候选窗口是**按真实当天日期动态生成**的：

```ts
// fallbackStatDates(): 从「昨天」起往前取 5 天
Array.from({ length: 5 }, (_, i) => new Date(Date.now() - (i + 1) * 86_400_000) ...)
```

于是日期一旦漂移，首个候选日就不再是 `20260924`，mock 的 502 分支永不触发，
`n >= 2` 断言失败——**测试随日历自动变红，与实现无关**。

修复方式：让"首个候选日"**动态**失败，而不是写死某一天：

```ts
const firstCandidate = Array.from({ length: 5 }, (_, i) =>
  new Date(Date.now() - (i + 1) * 86_400_000).toISOString().slice(0, 10).replace(/-/g, ''),
)[0]!
```

同时把断言从"某一固定日期被请求 ≥2 次"改为"尝试过 ≥2 个不同日期"，
使断言真正检验**回退行为**而非某个日期常量。

> 这类缺陷值得警惕：它平时是绿的，只在特定日期附近爆红，
> 复盘时极易被误判为"回退逻辑坏了"。

### 3.2 一处观察（非缺陷）

`mergeDatasets()` 合并策略是"后者只补前者没有的部分"，且**只处理 `hextechs`**。
新增数据源时若需要合并其它字段，这里会静默丢弃——见待办 T6。

## 四、真正的空白：悬浮窗的辅助内容

悬浮窗当前在 `InProgress` 阶段渲染的是：

> · 图鉴 / 胜率面板尚未实现（见开发计划）
> · 不识别你当前被提供的 3 个海克斯 —— 官方无此数据
> · 不替你做选择

这三行诚实，但也说明**对局中它帮不上任何忙**。这就是下一阶段的主战场。

关键判断：**别急着上 OCR**。本地已有 211 条海克斯胜率 + 1266 条英雄适配关系，
在不识别"你被提供了哪 3 个"的前提下，仍可提供大量**有依据**的辅助
（见 P1）。OCR 是最后一块拼图，不是第一块。

## 五、开发路线

### P0 — 收口与固化 ✅ **已完成**

| # | 任务 | 状态 |
|---|---|---|
| T1 | 提交既有改动（日期回退修复 + 文档重写） | ✅ commit `3e289ed` |

| T3 | 给 `data-store` / `data-cli` 补测试 | ✅ 14 + 7 项：原子写、损坏检测、新鲜度阈值、`mergeDatasets` |
| T4 | CI 化：`test` + `typecheck` + `build` | ✅ `.github/workflows/ci.yml`（windows-latest）|

**P0 执行附带的两项改进：**

1. **`cli.ts` 入口保护**。`main()` 原先是无条件调用的，导致任何 `import`
   （包括单元测试）都会立刻跑一遍 CLI、打印帮助并设置 `process.exitCode`——
   `mergeDatasets` 因此根本无法测试。已加 `isDirectRun()` 守卫
   （`import.meta.url` 比对 `process.argv[1]`，等价于 Python 的
   `if __name__ == '__main__'`），两条路径均验证通过：
   `import` 无副作用、`pnpm sync` / `status` 照常工作。

2. **`mergeDatasets` 的已知边界已钉成显式契约**。
   "只合并 `hextechs`" 这一行为现由测试固定：将来若新增第二个需要合并的字段，
   该测试会失败并提醒扩展，而不是静默丢数据。

**测试规模变化：24 → 60 项**（`core` 3 / `lcu` 8 / `cdragon` 12 /
`tencent` 16 / `data-store` 14 / `data-cli` 7），三项闸门全绿。

### P1 — 悬浮窗"对局中有用"（核心价值，不碰 OCR）✅ **已完成**

| # | 任务 | 状态 |
|---|---|---|
| T5 | 排行榜接进主进程 + 国服 ID 桥 join | ✅ 启动时算一次；`readRankings` + `buildRankBoard` |
| T6 | 对局内展示：按稀有度分组的强度榜 | ✅ 棱彩/黄金/白银，组内按胜率降序，每组 6 条 |
| T7 | 我方英雄的适配海克斯 | ✅ 选人阶段显示；用官方 `bestHeroes` 反向命中 |
| T9 | 数据新鲜度提示 | ✅ 脚注标注来源 + 统计日期，过期时加 ⚠ |

**实现要点**

join / 分组 / 排序逻辑放在 `packages/core/src/rankboard.ts`（**纯函数**）。
这不是为了"分层好看"：悬浮窗需要管理员权限 + 真实桌面会话，
**CI 里根本跑不起来**，只有把逻辑抽成纯函数才能被单元测试覆盖
（新增 17 项测试，core 总计 20 项）。

T8（阵容搭档推荐）**未做**：`HeroRankEntry.bestPartners` 数据虽在，
但选人阶段队友英雄常未确定，此时推荐搭档价值有限，留待后续评估。

**一个刻意的措辞约束**：面板标题是「**我方英雄的高胜率海克斯**」，
不是「本局给你的海克斯」。它回答"这个英雄官方统计上哪些海克斯胜率高"，
**不**回答"你被提供了什么"——后者需要截屏 + OCR（P2）。
UI 里也写明了"不识别你当前被提供的 3 个海克斯"，避免误导。

**修复的一个真实缺陷**：脚注原本写成
`s.isBrawl ? 徽标 : 来源脚注` —— 于是恰恰在**展示推荐的选人阶段**
（`isBrawl` 为真），数据出处与统计日期被徽标替换掉了。
推荐内容却不标来源，是产品上的硬伤。已改为两者同时显示并分行排版。

## 六、建议的下一步

P0 / P1 均已完成。悬浮窗现在在选人与对局阶段都能给出**有官方统计依据**的
参考，但还有一处关键限制：它不知道**你当前被提供的 3 个海克斯**。

下一步二选一：

- **P2（截屏 + OCR）** —— 补上这块拼图，价值最高但工程量与不确定性也最大。
  建议先做可行性验证：固定分辨率下截取卡牌区，用**图标模板匹配**（554 条图标
  已在手）而非 OCR 文本，命中不了就静默降级。
- **P3（数据站增强）** —— 低风险、可并行。装备页数据已抓 870 条却无浏览页，
  属于"数据在手但没露出来"的浪费。

**建议先做 P2 的可行性验证**（一到两天量级的小实验）：
若图标匹配在真实对局截图上命中率不理想，就该果断转向 P3，
而不是在 OCR 上无限投入。
