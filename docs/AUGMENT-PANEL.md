## 一、结论：刷新时刻无法从任何接口拿到，只能看屏幕

| 事实 | 依据 |
|---|---|
| 刷新时刻**不固定** | 回合节奏不固定；玩家可重随（同一面板换三张卡）、可晚点再选、可关了再开 |
| LCU 拿不到 | `/lol-gameflow/v1/session` 只有阶段与对局元信息，无海克斯 |
| 游戏自带 Live Client Data API 拿不到 | 真机 `https://127.0.0.1:2999/swagger/v3/openapi.json` 全量核对：**24 端点 / 24 schema，`augment`/`cherry`/`kiwi`/`hextech`/`brawl` 零命中**（2026-09-25 实测，记录在已删除的 `docs/lcu-probe-findings.md`，见 git `b3e2208^`） |
| 还有一个未跑完的探针 | `POST /Help?format=Full`（原生 remoting 全量函数表）。[probe-help.ts](../packages/lcu/src/probe-help.ts) 就是为它写的，结论未记录 → 建议进对局时顺手跑一次，把最后一点不确定性关掉 |

因为**没有任何"现在该刷海克斯了"的外部信号**，任何"估算时间 → 到点截屏"
的方案必然漏（抖动/延迟）或错（屏幕本来就变暗）。成熟第三方工具同样采用
截屏方案，侧面印证没有隐藏接口。

### 局内能拿到哪些状态（Live Client Data API，官方文档确认）

游戏客户端自带 `https://127.0.0.1:2999`（**只在局内存在**；自签证书需跳过校验。
这是 Riot 文档化的 Game Client API，与 LCU 同类：不读内存、不注入、不解析封包）：

| 端点 | 关键字段 | 我们能用来干什么 |
|---|---|---|
| `/liveclientdata/gamestats` | `gameMode` / `gameTime` / `mapName` / `mapNumber` / `mapTerrain` | 确认模式；给日志对时 |
| `/liveclientdata/activeplayer` | **`level`**、`currentGold`、`championStats.*`（当前/最大生命、护甲、移速、技能急速…）、`riotId` | **我的等级** |
| `/liveclientdata/playerlist` | 每人 **`level`**、**`isDead`**、**`respawnTimer`**、`items`、`scores`、`summonerSpells`、`team` | **死亡状态 / 等级**（含队友敌人） |
| `/liveclientdata/playerscores?riotId=` | `kills` / `deaths` / `assists` / `creepScore` | 死亡次数（交叉验证） |
| `/liveclientdata/eventdata` | `Events[]`：`EventName` + `EventTime`（`GameStart` / `ChampionKill` …） | 事件流（含击杀/被击杀） |
| `/liveclientdata/allgamedata` | 以上全部一次取回 | 一次查询拿全量 |

**明确拿不到**：海克斯相关的任何字段或事件（真机 swagger 24 端点 / 24 schema 零命中）。
**即：三选一的「三个选项是什么」只能截屏读；但「面板该出现了」的前提条件
（等级 + 死亡）API 是给的。**

> ✅ **已真机验证（2026-10-05）**：`pnpm --filter @hexbox/lcu probe:live` 在真实对局中确认
> `activePlayer.level` / `allPlayers[我].level` / `.isDead` / `.respawnTimer` **全部存在**
> （`debug/live-probe.json` 有原始 payload + checklist）。
> 该模式的 `gameMode` 是 **`KIWI`**（`mapNumber` 12、`mapTerrain` Default）—— 这就是
> "海克斯乱斗"的代号，产品里可以用它 gate 这个功能。
>
> 两个观察项（不影响当前方案）：那次探测 `gameTime` 仅 13.6s 且 `allPlayers` 只列出 **1 人**
> （可能其他人尚未进 payload）；我们只用到"我自己"那条，所以无影响，但要读别人需再确认。
> 另外该模式 `runes` 返回 `null`。

### ⚠️ 出现规律（用户实测确认，务必按这个理解）

**海克斯出现要同时满足两个条件**：

1. **到达指定等级**（7 / 11 / 15 级），且
2. **死亡回泉水**；

此外**开局必定出现一次**。

**所以不要按等级预测**（我犯过这个错，记录以免重犯）：到 7 级时你可能正在
中路打架，面板要等**下一次阵亡**才出现 —— 可能是几秒后，也可能是两分钟后。
按等级升频会挑错时刻（升频时没面板，真出面板时早降回来了）。
触发点由**死亡时机**决定 → 任何预测都不可靠。

这也解释了"面板停留时长不固定"：它一直挂着，直到玩家选完。

**所以：不预测时间，只识别"面板在不在"的边沿。面板出现的瞬间就是刷新事件。**

```
closed ──连续 2 帧命中──> open(此时才做全分辨率识别与绘制) ──连续 2 帧未命中──> closed(清空)
```

## 二、判据（真机标定，勿凭印象改）

真实面板长这样（`debug/shots/inprogress-*.png`，4587×1920）：

- 三张大卡横排在屏幕中部：x = 0.298 / 0.441 / 0.583 起，各宽 **0.115**、
  间距 **0.020**，纵向 y = **0.179 ~ 0.666**（占屏高 48.7%）；
- 每张卡的边框是**亮象牙白双描边**（一对亮线相隔 ≈ 0.0083×宽）——
  投影会把它们拆成两条线，**mergeGap 必须 ≈ 0.010×区宽**才能合并
  （正是 [grid.ts](../packages/vision/src/grid.ts) 的 `findBands` 里记过的坑）；
- 卡片**内部近黑**（平均亮度 25~29），边框很亮（151~158）。

于是判据是「**卡片行结构 + 明暗对比**」：

1. **结构**：在卡片行搜索区跑 `grid.ts` 的 `detectCards`
   （等宽聚桶 → 互不相交链 → 小间隙 → 纵横比），要求重建出 2~3 张卡；
2. **对比**：每张卡 `内部亮度 < 40` **且** `边框环 − 内部 ≥ 70`。

实测区分度（`scripts/diag-augment-frames.mts` 跑的是**线上同一份代码**）：

| 帧 | 卡片 | 内部亮度 | 边框−内部 | 判定 |
|---|---|---|---|---|
| 面板（3 张真机帧） | 3 | 25~29 | **92~129** | ✅ 面板 |
| 正常游玩（5 帧） | 0~2 | 52~103 | −1~18 | ❌ |
| 选人界面（3 帧） | 0~2 | 53~83 | −1~55 | ❌ |

**为什么用"对比"而不是"边框绝对亮度"**：薄亮边框在降采样时会被邻域暗像素
平均掉 —— 同一张面板帧的边框亮度 1.0 分辨率 155 → 1/2 时 144 → 1/4 时 120，
而 1/4 分辨率下游戏画面最高也有 110，绝对阈值无法同时服务两种分辨率。
对比量在各分辨率下都稳（面板 92+，负样本 ≤ 55）。

**分辨率下限**：同一检测器在 **1146×480（全分辨率的 1/4）** 上三个正样本全中、
负样本全拒；再降到 573×240（1/8）**不稳定**（部分帧卡片重建失败）。
**门控截屏不得低于 1/4**（代码里会把更小的值夹回 0.25）。

### ✅ 真机端到端验证（2026-10-05，一局真实对局）

门控跑在 **1147×480** 画布上（流是原生 3440×1440 → 约 1/3），结果：

| 指标 | 实测 |
|---|---|
| 面板帧（持续约 3 秒） | **3 张卡**：内部 **27/28/26**，边框 **137/140**，对比 **~110**（阈值 70） |
| 游戏画面帧（100+ 帧） | 卡片数 0~2、内部 **72~109** → **全部拒绝，零假阳性** |
| 面板出现边沿 | t≈8.1s 开出、t≈11.1s 消失（玩家选完） |
| 开门前的 2 帧 | 对比 65/67（**低于 70**）—— 卡片淡入动画，属"出现前"，不影响 |

即：**判据在真实游戏里成立，且余量充足**（对比 110 vs 阈值 70；负样本内部 72+ vs 阈值 40）。
另有两条假阳性防线的真实证据：我的桌面上（浏览器/窗口）曾出现"2 张结构相似的卡片 +
内部 104" → 被 `内部 < 40` 拒掉。

> 观察：面板**淡入的最初 1~2 帧**对比可能低于阈值。因为那时还没算"已打开"，
> 只会让开出边沿晚 0.25~0.5s，不影响正确性；但若将来把 `contrastMin` 收紧，
> 要留意这个淡入窗口。

### ⚠️ 已废弃的旧判据：相对基线压暗（EMA）

第一版门控判"中区相对基线是否变暗"。**这个设计有真实缺陷，已删除**：

真机录制恰好从"面板已经打开"开始（`debug/augment/closed-sample-1.png`
就是一张面板帧），基线被播种成面板的暗值 37；随后正常游玩更亮（中区 80~110）
→ `dimDrop` 恒为负 → **门控自锁，整局 0 次命中**。
绝对量 + 结构判据没有这个失效模式，也不需要维护任何跨帧亮度状态。

## 三、两级检测（廉价门控 → 昂贵确认）

| 级 | 频率 | 输入 | 做什么 |
|---|---|---|---|
| **门控**（已实现） | 常态 1000ms / 命中后 250ms（见下） | 低分辨率画布（1/4，约 1147×480） | 结构 + 对比判定 → 开/关边沿 |
| **确认**（S5.3） | 仅在门控命中时 | 一次性全分辨率截屏 | 定位三张卡 → 识别海克斯 → join 强度 → 绘制 |

去抖：连续 2 帧命中才开、连续 2 帧未命中才关。面板停留 ≥7 秒（两张真机帧
相隔 7 秒都在面板上），所以几百毫秒的确认延迟可忽略，换来的是不被卡片飞入
动画与单帧闪烁骗到。

分工（这个结构是性能结论逼出来的）：**检测在渲染端**
（`@hexbox/vision/browser` 的纯函数 —— 那里拿得到画面），**状态机在主进程**
（它决定何时取证、何时绘制），两者只传一个小 JSON，不传像素。理由见 §四。

### 节流：常态低频 + 命中后高频（一局只出现 4 次）

海克斯面板一局只出现 **4 次**，一直高频纯属浪费；而它**什么时候出现取决于
你什么时候死**（见 §一 的出现规律），又没法预测。所以：

| 模式 | 间隔 | 占空比（每帧约 17ms） | 何时进入 |
|---|---|---|---|
| `idle` | 1000ms | ~1.7% | 常态 |
| `probe` | 250ms | ~6.8% | 看到**单帧**命中的瞬间 |
| `active` | 250ms | ~6.8% | 确认面板已打开；持续到"最后一次命中"之后 20s |
| 面板**停留期间** | **`HEXBOX_AUGMENT_REROLL_POLL_MS`（默认 400ms）** | ~4.3% | 覆盖上面几档：面板开着时 **两种触发方式都用它**（单卡刷新检测要按这个节奏比指纹，见 §十五）；面板一关立刻回到常态（api 模式 **0 = 一帧不取**、pixel 模式回到 `idle`/`active`） |

核心取舍：**升频不去抖，降频才去抖**。
去抖（连续 2 帧才算开）是为了不误报；但"多截几帧"只花一点 CPU，
而"漏掉一次三选一"就是整次功能失效。所以单帧命中立刻升频；
probe 期间若确认打开就长时间高频；若一无所获，6 秒后自动降频（误检代价有上界）。

`tail`（消失后仍高频 20s）**不是正确性所需**，只是"少一次升频延迟"：
面板关掉后再打开，1 秒一次的常态轮询也能在 ~1.3s 内抓回来。
所以它取小值 —— 它直接决定省了多少资源。

策略是纯函数（[augment-cadence.ts](../packages/vision/src/augment-cadence.ts)，
10 项单测），主进程按 `changed` 决定要不要下发 IPC；渲染端收到 `cadence` 指令后
**重开定时器**（`setInterval` 的周期在创建时就固定了，改变量不生效 —— 见 §六 #12）。

预期：4 次面板 ×（面板 ~20s + tail 20s）≈ 160s/1200s 处于高频，
其余约 **87% 时间 1 秒一次** → 相比"一直 250ms"省约 **7 倍**；
`report.json` 的 `cadence.share` 会给出实测占比。

## 四、性能：一次性截屏不可用，已改为常驻截屏流（真机基准）

`debug:augment` 三次真机实测（`debug/augment/bench.json`）：

| 方式 | P50 | 尺寸 | 枚举源数 |
|---|---|---|---|
| window @1.00 | 1032ms | 4587×1920 | 14 |
| window @0.25 | 731ms | 1147×480 | 14 |
| **window @tiny(16px)** | **707ms** | 16×7 | 14 |
| screen @0.25 | 532ms | 1147×480 | 1 |
| screen @1.00 | 584ms | 4587×1920 | 1 |

**结论：开销与像素量几乎无关** —— 缩到 16×7 仍要 707ms。固定开销来自
"每次调用重建截屏会话 + 枚举窗口"，**降分辨率救不了**；`screen` 省约 200ms
（少枚举 13 个窗口）但仍是半秒级。所以：

- **门控路径改为常驻截屏流**（`getDisplayMedia` 建一次流，之后逐帧取图）：
  主进程把屏幕源交给隐藏渲染窗口，渲染端每帧"画到小画布 → 取像素 → 跑检测"，
  只把一个小 JSON（found/cards/reason/耗时）回传；状态机与全分辨率取证在主进程。
  代码：[augment-stream.ts](../apps/overlay/src/main/augment-stream.ts) +
  [capture/worker.ts](../apps/overlay/src/capture/worker.ts)。
- **一次性截屏只用于"边沿取证"**（面板出现/消失时抓一张全分辨率帧），
  一块面板只有 1~2 次，半秒开销无所谓。

⚠️ 隐藏窗口的两个坑（已在代码里处理，真机出问题先查这里）：
`backgroundThrottling: false`（否则隐藏窗口的定时器被降到 ~1Hz）；
若 4 秒收不到帧说明"不合成就不解码"，就退到"显示但 `opacity: 0`"。
启动日志会写明用了哪条路。

`HEXBOX_AUGMENT_CAPTURE=oneshot` 可切回旧路径做对照（判断"是不是流的锅"）。

## 六、已确认的坑（每个都有真实来源）

| # | 坑 | 结论 |
|---|---|---|
| 1 | 用**相对基线压暗**（EMA）判面板 | ❌ 已删除。录制从面板打开时开始会让基线自锁，整局 0 命中（真实事故，见 §二末） |
| 2 | 用**边框绝对亮度**当判据 | ❌ 降采样会把薄亮边框平均掉（155→120），绝对阈值无法跨分辨率；改用「边框−内部」对比 |
| 3 | `mergeGap` 太小（0.004×区宽） | ❌ 双描边被拆成两条线，3 张卡检出 12 条线；应为 ≈0.010×区宽（grid.ts 早已记录该常数） |
| 4 | 复用选人阶段的**标签记忆 TTL** | ❌ 绝对不行。选人阶段"漏检时旧标签续显 6 轮"是有意义的（[label-memory.ts](../packages/vision/src/label-memory.ts)）；局内每次 offer 是**不同**的三张卡，跨 offer 沿用会把上一轮强度贴到新卡上。位置记忆只在**同一次 open 期间**有效，关闭边沿必须 `reset()` |
| 5 | 商店面板（回合间）像不像？ | 目前靠"2~3 张卡 + 内部暗/对比强"区分；商店是**多列小格**（>3 张即拒）。本轮负样本里未出现商店帧 → **仍需真机确认** |
| 6 | 坐标口径 | 搜索区是**窗口归一化**，用前必须经 `panelRowRectInCapture()`（内部 `windowRectToCapture`）。截屏可能是显示器快照，直接用会整体错位（S2 真机错位就是这个原因）。这也是它单独放在 `augment-region.ts` 的原因：换算要 PowerShell，不能进渲染端 bundle |
| 7 | `phase` 门控 | 局内门控循环与选人视觉循环**不是一件事**（区域、节奏、清空规则都不同），S5.4 接线时另开字段，不要合并成一个布尔 |
| 8 | 隐藏窗口跑定时器 | ⚠️ 必须 `backgroundThrottling: false`，否则被降到 ~1Hz；完全不可见的窗口还可能不合成（不出帧）→ 代码里有"4 秒无帧就显示但 opacity=0"的兜底 |
| 9 | `__dirname` 写死相对路径 | ❌ 同一个模块被打进 `dist/main/index.cjs` 与 `dist/debug-augment.cjs` 两个入口，`__dirname` **不同**：preload 与 `worker.html` 一个要同级、一个要上一级。写死任何一种必然在另一种里加载失败。改成**按存在性探测**（`resolvePreload` / `resolveWorkerHtml`）。这与主进程里记过的 `join(__dirname,'preload')` 是同一类坑 |
| 10 | 异常静默挂死、零产物 | ❌ `loadFile` 的 reject 冒到 `whenReady` 链之外后，Electron **不报错也不退出** —— 用户看到"跑完了却什么都没有"。现在加了 `unhandledRejection`/`uncaughtException` 兜底（打日志 + 退出），并且"读不到 LCU 凭证"不再直接拒绝录制（只警告），只有**明确知道不在对局中**才拒绝 |
| 11 | 第一帧就做全分辨率采样 | ❌ `lastClosedSampleAt` 初值 0 会让 `now - 0 >= 30000` 恒真 → 开局就白截一张全分辨率图。改为用 `startedAt` 初始化 |
| 12 | 改了间隔却不生效 | ❌ `setInterval` 的周期在**创建时**就固定了，改配置变量不会生效 → 收到 `cadence` 指令必须 `clearInterval` + 重开。已用自测锁住（下发 250ms → 实测 244ms） |
| 13 | **按窗口名找游戏窗口**（`sources.find(s => s.name === 'League of Legends')`） | ❌ 真机上它命中的是**客户端窗口**（3413×1920，"游戏仍在进行中……"）而不是游戏窗口 → 存下来的"面板帧"里根本没有卡片。门控走的是 getDisplayMedia 的**屏幕**源，取证也必须用**屏幕**源，两者才在同一坐标系。**边沿取证已改为 `screen`**（JSON 里记 `source` 便于核对） |
| 14 | 边沿取证 `await` 阻塞主循环 | ❌ 一次取证约 **1.7s**（getSources ~600ms + toBitmap + toPNG），期间渲染端照常推帧、消息排队，回头一次性处理会**凭空造出一对 close/open 假边沿**（这次真机就发生了）。修法三条：① 不 `await`（`void save` + in-flight 守卫）；② worker 在报告里带**采集时刻**，主进程**丢弃 >1.5s 的过期帧**；③ 不再在运行时生成 `annotated.png`（JS 编码 3440×1440 太贵），需要标注图时用离线脚本画 |

> 修复后的验证（本地真实桌面，非游戏）：`closed-sample-1.json` 里
> `"source": "整个屏幕"`、`capture: 4587x1920`、`tookMs: 893`（原来 1746）。

| 15 | **对局中抓全分辨率取证帧 → 系统光标卡约 1 秒** | ❌ 2026-10-05 用户实测：一局卡 3 次，与我这边 3 次取证的**时间戳完全对齐**（18:40:40 / 18:41:11 / 18:41:41）。`desktopCapturer.getSources` 是 **DWM/合成器级**卡顿，不是"我们进程自己慢" → **异步化救不了**。处置：**默认关闭**（`HEXBOX_AUGMENT_FORENSICS=1` 才开，常态样本默认 0）。正解：在**渲染端**从已有的屏幕流取全分辨率帧（`drawImage` + 裁剪），不经 desktopCapturer、也不把整帧搬回主进程 |
| 16 | **窗口矩形探针认错窗口 → 搜索区切掉卡边框 → 整局 0 命中** | ❌ 2026-10-05：游戏其实**全屏**（那帧里 HUD 铺满整帧、FPS 238），探针却给出 `1600×900 @ (347,6)` 的**别的**窗口 → 映射出的区为 x 0.3047~0.6953，比真实卡片 x 0.298~0.698 更窄，**外侧边框被切掉** → 该局 `foundFrames=0`。修法：**两个候选区都搜**（主区 + 全屏恒等区，多花 2~4ms）；**不去猜**"探针可不可信"——窗口化游戏给出的正是"小而不等比"的矩形，猜错会把窗口化支持弄坏 |

> ⚠️ 事故 16 还暴露一个**连锁**：状态机只在"门控**看见**卡片又消失"时消耗一次待选
> （有意如此：看不见就不该假装选过了）。所以门控一瞎，`pending` 永不减少 ——
> **API 触发再准也拿不到东西。两件事必须同时对。**

> ⚠️ `apiFallback` 的配套修正：一旦连续 5 次拿不到 2999 而退回像素节流，
> **就不能再让 API 控制开关**（否则两条策略互相抢：实测开局前 API 不可用 → 退回像素节流
> → 之后 API 恢复又把间隔改成 0 → 面板期间一帧不取）。

| 17 | **指纹库按 `process.cwd()` 找 → pnpm 下 cwd 是包目录 → 库为空 → 识别全灭** | ❌ 2026-10-05 完整一局：门控抓到 **3/3** 次面板（`pending` 正确收敛到 `[15]`）、全分辨率取帧 3440×1440/45ms 也正常，但 **9 张卡全部"认不准"**。原因：`pnpm --filter … debug:augment` 把工作目录设成 `apps/overlay`，于是去找 `apps/overlay/data/augment-names.json`（不存在）→ 指纹库为空 → 每张卡都认不出（**不报错**，所以表现是"识别全灭"而不是崩）。`OUT_DIR` 早就有"向上回退"，只有这里漏了。修法：与主 overlay 同一套——**向上遍历、以 `data/dataset.json` 是否存在为准** |
| 18 | 对局结束后程序不停（LCU 阶段读不到时的盲区）| ❌ 用户实测："打完游戏程序还在跑，只能手动 Ctrl+C"。跟随模式原本只靠 LCU `phase`；而非管理员终端**读不到 LCU 凭证**（见 `packages/lcu/src/detect.ts` 的策略 0 事故）→ `phase` 恒为 null → 永远不停。修法：LCU 不可读时用**游戏窗口是否还在**兜底（连续 3 次探不到窗口 = 对局结束）|
| 19 | Ctrl+C 收不到（Electron 是 GUI 子系统进程）| ❌ 真机实测：Ctrl+C 后整局产物没落盘。Windows 的 `CTRL_C_EVENT` **只送给挂控制台的进程**，Electron 主进程收不到，`process.on('SIGINT')` 是死代码。修法：由挂控制台的 launcher（`run-electron.mjs`）收到信号后写**哨兵文件**，录制程序轮询到再干净收尾；另加 15 秒一次的 `checkpoint.json`（强杀也能留下识别结果与触发状态）|

## 七、产品决策（2026-10-04 ~ 10-05 与用户确认）

- **局内不要侧边窗**：局内信息载体是"海克斯卡上的强度标签"。
  `decideVisible().showPanel` 现恒为 `false`
  （[visibility.ts](../packages/vision/src/visibility.ts)），侧边窗代码留到 S4 删除。
- **认不准就不画**：`found=false` 一律不绘制，不画"未识别"占位框。
- **查不到强度也不画**：该英雄的强度表就是该英雄能出现的池（上游每英雄 95~162 条，
  实测**不是**我们截断，见 §十二「强度表的覆盖度」）；官方页没有"跨英雄同档位泛用表"
  这个口径，因此**不做兜底** —— 查不到就不画，绝不按稀有度猜一个档位。
- **强度标签画在卡片底部空白区、水平居中**（2026-10-05 用户定，随后给了参考图）：
  卡内 y 0.72~1.0 目前是空的（上方依次是图标 0.07~0.37 / 名字 0.44~0.51 /
  稀有度标签 0.52~0.55 / 描述 0.60~0.72），放这里不遮挡任何既有信息。
  实测最长的一帧描述到 **0.713**（横向只到卡片两侧的角饰），中央列一直空到底部内框 ≈0.96。
- **外观 = 卡下方正中间的「大号描边字母 + 尖括号 + 选取率」**（2026-10-05 用户给
  虎牙助手的参考图后定稿；前两版 —— 0.76×0.20 通栏横条、"右下角小圆角徽章" ——
  都被否掉）：
  · **没有色块底**；主元素是**大号加粗彩色字母**（2026-10-06 三次缩小 + 一次纵向
    修正之后：占卡高 **0.066~0.074**，**默认档 0.066 = `small`**），
    带**深色描边 + 同色外发光**，两侧各一个同色尖括号 `‹ S ›`；
  · 字母下面一行小字 **「选取率 12.1%」**（字号 ≈字母的 1/3、中性浅灰）；
  · 字母（含那圈发光外廓）与选取率行之间**必须留正间隙** —— 真机像素实测三档
    **+4.7 / +4.7 / +5.3 DIP**（改前是三档全部重叠，见 §十三）；
  · 三档预设（小/中/大 = 离线预览里的候选 1/2/3）见 §十三。
- **每张卡最多刷新一次；刷新发生在面板保持打开期间**（2026-10-06 用户说明，
  机制见 §十五）：面板**不会**因为刷新而关闭，所以刷新**必须**由"每张卡的画面
  内容变化"发现，并把那张卡的标签**重新识别 + 替换**；新卡**认不出**或
  **该英雄强度表里查不到** → **该卡标签必须消失**（绝不能留旧字母 —— 那会把
  上一颗海克斯的强度贴到新卡上，比不显示更糟）。**只重认变化的那张卡**，
  其余两张不受影响。
- **标签内容 = 强度评级字母 + 一行选取率**（2026-10-05 用户定，对齐 101 官网的
  「强度」列与「登场率」列）。数据现成：`augment_json_irank` →
  `provider-tencent.parseChampionAugments()` 的 `tier` + `pickRate`
  → overlay main `augmentTierTable()` / `augmentPickRateTable()`。
  ⚠️ 选取率**查不到/为 0 时那一行不画**（字母照画）—— 绝不为了版面完整补一个猜出来的数。
- **常态不截屏**（2026-10-05 用户定）：由 2999 的「死亡 + 等级达标 + 该次未选」触发
  （见 §九），而不是常态低频截屏。
- **识别以 OCR 为主、图标只做同名消歧**（2026-10-05 用户定）。
  这个优先级在 dataset 上得到支持：KIWI 共 **218 个海克斯、218 个不同名字、0 重名**
  → 认对名字即可 join 到唯一 id，**图标通道当前不需要**。
  图标匹配的探索记录（为什么暂时搁置）见 §五末尾。
- **档位配色与清空规则**（2026-10-05，S5.4c；配色按参考图对齐）：
  S **金** / A **红** / B **青蓝** / C **中性灰**
  （`vision/augment-tier-label.ts` 的 `AUGMENT_TIER_COLORS`，见 §十三 的色值表）——
  字母、尖括号、发光**同一个颜色**（只是 alpha 不同），所以只有一个来源；
  上游将来加档时**给中性灰、字母照画**（不猜档位）；面板**关闭边沿立刻清空**标签 ——
  **不复用**选人阶段那套 6 轮 TTL（局内每次 offer 是不同三张卡，见 §六 #4）。
- **画布只有一块**：局内标签与选人标签共用
  [main/label-overlay.ts](../apps/overlay/src/main/label-overlay.ts) 创建的全屏透明画布
  与 `overlay:vision` 通道（渲染端 `renderer/overlay-canvas.ts`），不新建平行窗口代码。

## 八、识别：卡面名字 OCR（S5.3）

代码：[vision/augment-ocr.ts](../packages/vision/src/augment-ocr.ts)（纯函数，10 项单测）。
复用选人阶段英雄名的同一套机制（二值化 → 裁文字包围盒 → 拉伸到固定网格 → 与渲染
指纹库做 Jaccard），但**名字带位置完全不同**：

| 卡片 | 名字带纵向中心（卡内） | 依据 |
|---|---|---|
| 选人卡（`NAME_STRIP`）| **0.856**（下部）| 2026-09-27 标定 |
| **海克斯卡**（`AUGMENT_NAME_STRIP`）| **0.470**（中部）| 2026-10-05 实测 |

海克斯卡布局（真机 571×889 卡内实测）：图标 y 0.07~0.37 → **名字 y 0.44~0.51**
→ 稀有度标签 0.52~0.55 → 描述 0.60~0.72。直接套 `NAME_STRIP` 会切到描述文字上。

指纹库：`scripts/render-augment-name-fingerprints.ps1` → `data/augment-names.json`
（Microsoft YaHei **Bold** 40px，218 条）。

### 标定数据（真机两帧、共 6 张卡 / 3 个不同名字）

| 字体库 | 正确项得分 | 分差 | 结论 |
|---|---|---|---|
| **Bold@40** | **0.62 ~ 0.73** | **0.07 ~ 0.17** | ✅ 采用（卡面是粗体）|
| Regular@40 | 0.45 ~ 0.61 | 0.02 ~ 0.19 | 分数明显更低 |

- 纵向中心 0.462~0.475 都稳；**≥0.488 会吃到下方稀有度标签**，并出现
  `威能之追求 → 急速之追求` 这类近似混淆 → 所以**必须有分差规则**（`minMargin 0.03`）。
- 阈值 140/160/180 都成立（Bold 0.62~0.73）→ 取中值 160。
- 默认：`minScore 0.55`（正样本 ≥0.62，留余量）、`minMargin 0.03`。
  认不准返回 `null`，调用方不画（宁漏勿错）。

**线上默认参数在真机帧上的复验**（跑的是同一份代码）：
`缩小引擎 0.69/0.11`、`夜狩 0.71/0.17`、`威能之追求 0.64/0.08` —— 全对。

> ⚠️ **样本仍偏少**：只有同一局的三选一（3 个不同名字）。混淆风险最高的是名字相近的
> 组合（急速之追求 / 威能之追求 / 缩小引擎 / 坦克引擎 …）。下一局录制会补充样本，
> 届时用 `scripts/diag-augment-name-ocr.mts --sweep` 复标定阈值与分差。

## 九、常态不截屏：API 触发（S5.6，用户方案 2026-10-05）

既然 2999 能给出 `level` / `isDead`（§一已真机确认），就**不需要常态截屏**了：

```
常态：一帧不取（间隔 0）
   ↑                                   ↓ 触发
   └── 选完（截屏看不到卡片）──────── 开截屏（250ms）
```

**两个信号分工明确**：**API 决定"什么时候看"，像素决定"看到了什么"。**

- **触发器**（纯函数 [augment-trigger.ts](../packages/vision/src/augment-trigger.ts)，14 项单测）：
  维护"还没选的海克斯等级集合" `pending`（默认 `[0, 7, 11, 15]`，0 = 开局那次）。
- **开**：① 开局（`gameTime ≤ 25s` 且开局那次未选）；② **死亡**（`isDead` 上升沿）
  **且**存在未选等级 ≤ 当前等级。
- **关**：门控报"卡片消失"（= 选完一次）且**本轮够格的都选完了**。

### ⚠️ 连选（用户特别提醒，也最容易写错）

**未选的海克斯会累积**：开局出门后一直没死，直到 11 级才死亡 ——
那时 7 级和 11 级**两次都还没选**，游戏会**连着弹多次三选一**。

所以：① 状态必须是"未选**集合**"，不是"当前等级那一次"；
② 关掉一次之后若还有够格的未选，**保持开截屏**（`chainGraceMs` 默认 20s）等下一次弹窗，
不能立刻关掉，否则第二次三选一整个漏掉。

### 自愈（每条都对应一种真实失败）

| 情况 | 行为 |
|---|---|
| 门控漏检面板（只收到开边沿没有关边沿）| `armWindowMs`（45s）到点自动关；**pending 不丢**，下次死亡再试 |
| 玩家一直在思考（面板开着）| **只要门控说还开着就绝不超时**，并顺延窗口 |
| 工具在对局中途启动 | 首帧若 `gameTime > 60s`，把"开局"那次按已选处理（否则第一次死亡会误判成连选）|
| 2999 拿不到（未进游戏 / 被拦）| 连续 5 次失败 → **退回像素节流**并告警，保证这一局仍有数据 |
| 关边沿重复上报 | 只认"开 → 关"周期里的那一次关（多消耗一次就会漏掉一整个海克斯）|

## 十一、验收标准

1. 面板出现 → 三张卡下方都有该英雄的强度标签；识别不确定的卡**不画**；
2. 面板消失 → 标签**立刻**清空（不得残留到下一次三选一）；
3. 商店/死亡/结算/大厅/选人**不得**触发绘制；
4. 不影响游戏帧率（§四的基准结论落到代码里）；
5. **面板保持打开期间刷新某张卡 → 该卡标签跟着变**（重认成新档位）；新卡认不出
   或该英雄查不到强度 → **该卡标签消失**，其余两张不动（§十五）；
   且**整排标签的位置一个字都不许动** —— 纵向基准在开边沿锁定，刷新只改内容
   （回放：`scripts/diag-augment-row-band.mts` 必须打 `0.000000 DIP`）；
6. 纯函数部分有单测，真机帧的数值补进回归用例；
7. 三闸门（test / typecheck / build）保持绿。

### 覆盖窗自测：把"窗口可见性"从"识别/几何"里隔离出来（2026-10-05）

真机出现"`report.json` 里 `drawn: true`、坐标也在屏内，但游戏里一个字母都看不到"。
这类问题**不能靠一局真机反复试**，所以做成开关（不需要游戏）：

```powershell
$env:HEXBOX_LABEL_OVERLAY_TEST='1'; pnpm --filter @hexbox/overlay debug:augment
# 同一块画布、同一份窗口代码（常驻 overlay 入口也一样）：
$env:HEXBOX_LABEL_OVERLAY_TEST='1'; pnpm dev:overlay
```

屏幕上出现左 **L** / 中 **C** / 右 **R** 三个大方块（约 300×200），5 秒后自动退出；
终端打印 `visible / alwaysOnTop / bounds`、三个标签中心的**画布像素**（`getImageData`）、
截图 `debug/label-overlay-selftest.png`，并给出 ✅/❌ 结论。

> 窗口参数与已验证可用的 S2 选人标签**完全一致**（同一份 `label-overlay.ts`），
> 所以差异不在创建参数，而在**时序与环境**：S2 每 1.5 秒推一次、画在**客户端窗口**上；
> 局内是**一局只推一次**、且要盖在**游戏窗口**（无边框全屏，会不断抢回 z 序顶端）上。
> 只推一次 + 被遮挡窗口的合成节流（`backgroundThrottling`）= 那一次帧没被合成，
> 就再也没有机会显示。
>
> 因此 `label-overlay.ts` 现在：① 每次推送重申 `alwaysOnTop('screen-saver')` + `moveTop()`；
> ② 标签在屏期间**每 1 秒重申置顶并重推一次内容**（重绘强制走一次合成），
> `active:false`/清空时停掉；③ `backgroundThrottling: false`。
> **几何保持不变**（坐标/缩放没动）。

要点：

- **内容两行**：上面是**档位字母**（`text` = S/A/B/C），下面是**「选取率 12.1%」**
  （`subText`，一位小数、按该英雄口径的登场率原样换算；缺失/为 0 → 空串 = 不画那一行）。
  两行都由 `augmentTierLabelsLocked()`（无锁形态 `augmentTierLabels()`）这个**纯函数**给
  —— 渲染端不拼字符串、不算百分比。
- **配色**：`AUGMENT_TIER_COLORS`（S 金 / A 红 / B 青蓝 / C 灰，见 §十三）；
  上游将来加档 → 中性灰 + **字母照画**（不猜档位）。渲染端可选字段 `color`：
  有它用档位色（字母填充 / 尖括号 / 发光都由它派生），没有就沿用选人标签的绿/灰。
- **样式与大小**：由**标签预设**一处决定（`AUGMENT_BADGE_PRESETS`：整条宽/高/留白/字号比例），
  随屏幕坐标一起下发的 `fontScale` 告诉渲染端"字号占框高的几成"、
  `style: 'tier'` 告诉它走"大字母 + 尖括号 + 选取率行、没有色块底"那条绘制路径 ——
  渲染端**不再**按框高自己猜比例、也不自己摆尖括号（徽章的框比选人标签矮得多，
  猜出来的字号会与离线预览不一致）。换档：`AUGMENT_BADGE_DEFAULT`（默认 `small`）
  或临时 `HEXBOX_AUGMENT_BADGE=medium|large`。
- **画布只有一块**：`main/label-overlay.ts` 提供创建/定位/推送；选人阶段
  （`main/index.ts`）与局内标签（`debug-augment.ts`）**共用**它，没有第二套窗口代码。
- **清空规则**：面板**关闭边沿**（`reading.edge === 'close'`）与收工（`finish()`）
  都调 `clearLabelOverlay` → 推 `active:false`；**不复用**选人阶段那套 6 轮 TTL
  （`label-memory.ts`）—— 局内每次 offer 是**不同**的三张卡，残留会把上一轮强度贴到新卡上（§六 #4）。
- **不会自己骗自己**：标签矩形永远在卡内（默认预设 = 居中 0.30×0.114 卡尺寸、距底 0.07；
  整排纵向基准**开边沿锁定**（2026-10-06 二次验收，见 §十三 末尾）——
  锁定用的是这一排**要画的卡**的冻结矩形，之后刷新不再改它，
  所以至多只有比基准**更矮**的那一张理论上会贴到自己的底边，
  而真机实测的离群卡（重随动画里）只会**更高**，实测三张都在卡内），
  **不覆盖卡片的亮边框** —— 门控的「结构 + 对比」判据既不会被自己挡住，
  也不会把自己的标签误判成卡片（标签**没有色块底**，只有字母/尖括号/一行小字；
  门控在 1/4 分辨率下工作时这些笔迹更细，相邻间隙校验也会拒掉它）。
  另外画布在截屏流里可见（它就是屏幕内容的一部分），这条"不干扰"是必须的性质。
  ⚠️ 同一个道理也适用于**单卡刷新检测的指纹**：取样区下沿停在卡内 **0.74**
  （标签从 0.788 起），所以"我们自己画上去的字母"不会让指纹变化（见 §十五）。

- 已同步的 173 个英雄（`data/builds.json`）：每条 **95 ~ 162** 条，中位数 **126**，均值 **125**，
  合计 21644 条；**0 条空 tier、0 条重复 augmentId**（tier 取值只有 S/A/B/C）。
- **全量口径的交叉验证**：173 个英雄强度表的并集 = **211** 个不同 ID，

  另有 1 个 ID（1379）**有**强度但不在我们冻结的图鉴里（图鉴落后于统计）。
- **没有分页、没有更全的字段**：`page`/`pagesize`/`pageno`/`augmentid_level` 实测**不改变**条数；
  同接口的 `augment_json` 只是**每品质前 10**、**5 列（没有强度列）**、**没有 `255` 组**
  → 拿它"补覆盖率"只会得到没有强度的行。**故 Provider 刻意不采集 `augment_json`**
  （`RawHeroDetail.augment_json` 有注释说明），并有单测锁住它解析出 0 条。

**结论与纪律**：

1. **不编造强度**：官方页没有「跨英雄的同档位（白银/黄金/棱彩）泛用表」这个口径
   （全局榜只有登场率/胜率排名，没有「强度」字母）→ **不做兜底**，查不到就**不画**（现行行为正确）。
2. **0/N 命中是"英雄认错"的强信号**：该英雄的池就是这局能出现的池，认对英雄时
   那张表就是这局可能出现的全部卡片，几乎不可能 13 张**全部**落在表外。
   ⚠️ 真机第 1 局正是**英雄认错**：玩无极剑圣（11）却解析成 154（生化魔人），
   而 AD/暴击向的海克斯只在 11 的池里（11 的 `255` 组里 `1356 暴击飞弹` 排第 1、tier S）。
3. **但反过来不成立：N/N 命中 ≠ 英雄认对**（别把"全画出来"当成身份校验通过）。
   173 张表里有 **31** 颗海克斯是**全表都有**的（质变：棱彩阶/缩小引擎/属性叠属性！…），
   任意两张表平均重合 ~60%（样例 90/108）。认错英雄时，只要三张卡都落在泛用池里
   就会 9/9 全中 —— 真机第 2 局正是这种假阳性（玩酒桶却解析成 43 天启者）。
   **身份只认"我自己"这个来源**，不靠命中率反推。
4. 回归单测见 `packages/provider-tencent/src/herodetail.test.ts` 的「覆盖度」一组
   （真实形状夹具：6 列、`255`+三品质分组；锁住不截断、并集相等、`augmentId` 键名）。

### 三档预设（真机 3440×1440：卡片 427×667 物理像素 = 284.7×444.7 DIP）

**2026-10-06 第三次定尺寸**（用户第二次反馈："**字体似乎没变，还是太大**"）。
先说归因，因为它决定了改法 —— **不是链路没生效**：

#### 「新尺寸到底有没有生效」是量出来的，不是猜的

用**渲染端真实产物**（`apps/overlay/dist/renderer/overlay.html` +
`overlay-canvas.js` + preload）逐条推 `style:'tier'` 标签、截图后按像素分类量
（`debug/tier-canvas-render.cjs` + `debug/measure-tier-canvas.mts`；
计划值来自线上纯函数 `debug/tier-plan.mts`）：

| | 计划 cap 高 | **实测字母墨迹高** | 实测深色描边外扩 | 实测发光外扩 | **实测整条外廓** | 外廓 / 字母 |
|---|---|---|---|---|---|---|
| 上一版 `0.44×0.19`（cap 11.9%）| 52.5 DIP | 54.0 DIP | +4.0 DIP | +21.7 DIP | 110.7 × **105.3** DIP | 1.95× |
| 现在 `0.37×0.136`（cap 8.5%）| 37.8 DIP | **39.3 DIP** | +2.7 DIP | +15.3 DIP | 80.0 × **75.3** DIP | 1.92× |

- 实测缩幅 **−27.2%** 与计划缩幅 −28.0% 一致（实测/计划 = 1.03~1.04，那一点点是
  `S` 这类圆字母的**上下出格**与抗锯齿，两版一致）→
  **新尺寸确实作用到了屏幕上**：不存在旧值、缓存、没重建或环境变量覆盖
  （真机验收产物 `debug/augment/report.json` 里 `labels.preset` 记录的就是
  `medium / 0.136 / fontScale 0.8915`，`HEXBOX_AUGMENT_BADGE` 没有覆盖它）；
- 那为什么用户还是觉得大？因为**用户看到的"字"是那一圈光晕**：
  深色描边向外扩半个线宽、发光再向外扩 `0.32 cap`，合起来
  **整条外廓 ≈ 字母墨迹的 1.9 倍**（75.3 vs 39.3 DIP，外廓外扩合计 18.0 DIP）。
  所以"缩小 29%"在外廓上同样只缩小 29% —— 观感仍然偏大，属于**观感问题，不是链路 bug**；
- 结论：**继续缩**。而且描边/发光本来就是 `cap 高`的比例（`TIER_TREATMENTS`：
  描边 0.15 cap、发光 0.32 cap —— 第四次修压字时发光收到 **0.28 cap**），
  所以缩 cap 时它们**自动同比例收**，
  实测"外廓/字母"比在 1.95→1.88 之间几乎不变 —— 光晕不会"缩得比字母慢"。

**三档新值**（下表是真机数值，`scripts/preview-augment-labels.mts` 打印的那一份；
2026-10-06 第四次只改**纵向**，字母那几列**一个像素都没动**）：

### 行对齐：同一排三个标签必须在**同一个高度**（2026-10-06）

用户："**同一排三个标签明显不在一个高度上**"。

**根因**：标签的纵向位置原本是 `card.y + zone.y × card.h`，即**每张卡各自的**
检测矩形。面板打开那一帧三张卡的矩形通常完全一致（实测 `debug/shots/inprogress-*.png`
两帧的 Δy = Δh = **0.00 px**），但**单卡重随**时只有被刷新那一张会重新全分辨率
识别（`augment-reroll.ts` 的 `mergeRefreshedCards()` 用**新**矩形替换旧矩形，
另外两张保留冻结矩形），而重随那一刻卡片**正在翻牌动画里** → 那张卡的矩形又高又靠上。

**真机量化**（`debug/augment/report.json`，atMs=23221，用户那次验收的原始记录；
用报告里记录的预设 `0.37×0.136` 反推卡片矩形，再按**当前默认档**算标签；
单位 = 屏幕物理像素，基线 = 字母 cap 带下沿）：

| | 卡 rect（归一化）| 标签框顶 y | 字母 cap | 基线 |
|---|---|---|---|---|
| 卡 1 / 卡 2（冻结矩形）| y=0.191705 h=0.460611 | 825.3 px | 46.2 px | 871.7 px |
| 卡 3（重随那一刻重认）| y=0.172871 h=0.497603 | **842.2 px** | **50.4 px** | **892.5 px** |

即 **y 差 17.0 像素、基线差 20.8 像素**（改用当前的更小档位后差得更多：`zone.y`
更大，卡片高度差被放大），而且那张卡的字母还大一号 —— 肉眼就是"不在一个高度"。

**改法**：`packages/vision/src/augment-label.ts` 新增两个纯函数
（`labelRowBand()` / `alignRowLabels()`），`resolveAugmentTiers()` 改成
**先把这一排真正要画的卡过滤出来，再用这些卡片矩形的中位数推出唯一的纵向基准**
（`h` 与 `y` 都取中位数）：

- **纵向**：三张标签共用同一个 `y` 与 `h` → **基线像素级相同**（实测 0.0 px）；
- **横向完全没改**：仍是每张卡各自水平居中（横向从来不是问题）；
- 取**中位数**而不是均值：三张里那张在动画中的（明显偏大）不该把整排拉走；
- 退化情况：空数组 → `[]`（不画）；单张卡 → 与 `augmentLabelRect()` **逐位相同**；
  两张卡 → 中位数 = 两者均值，仍共用一个基准；卡片数量变化都不崩；
- 行基准只由**要画的卡**决定：某张认不准（标签消失）时，剩下几张重新成排，
  不会让已经画出来的标签跟着乱跳；"认不准/查不到不画"的过滤语义**未改动**；
- ⚠️ 代价（明确写下来，别当成没想到）：整排共用一个 `h` 之后，比中位数**更矮**的
  那一张卡上的标签会相对它的卡底多占一点 —— 中位数是"中间那张"，最多只有一张会
  偏矮，而真机实测出现离群的是**更高**的重随动画卡（三张都在卡内）；
  真要用逐卡几何的"恰好距卡底 6%"就得放弃基线一致，两者不可兼得，**以基线一致为准**。

单测：`augment-label.test.ts`（真机重随帧的三张卡 → y/h 完全相等、横向仍居中、
退化情况、`median()` 本身）与 `augment-tier-label.test.ts`（走
`augmentTierLabels()` 的端到端行对齐、过滤语义不受影响）。
离线预览里的 `[ROW ALIGNED]` 段与终端"行对齐核对"一节都走同一条路径
（一次 `augmentTierLabelsLocked()` 调用 = 那一帧锁定一次），所以**预览与局内同源**。

### 行基准的**锁**：开边沿锁定，面板关闭前一直复用（2026-10-06 二次验收）

用户二次验收："**某次单卡刷新后，三个标签整体下移了一点**（但彼此仍同一高度）"。

**根因：中位数只抗离群，不保证不变。** 上一版把整排基准交给"这一排卡片矩形的
中位数"，而重随重识别会把**被刷新那张卡**的矩形换成"翻牌动画中间帧"的矩形
（`mergeRefreshedCards()` 的语义，见 §十五）——`{a, b, c}` 变成 `{a, b, c'}`：

- 一个值变了、且新值**落在另外两个之间** → 3 个数的中位数**就是那个新值** → 整排平移；
- 真机 `debug/augment/report.json` 那两份冻结矩形**逐位相同**，所以第一次重随
  （atMs=14150）中位数没动，**第二次重随**（atMs=17750，三张里两张已成动画矩形）
  才跳：`y 0.189621 → 0.179117`、`h 0.463389 → 0.487192`
  → **三个标签一起下移 12.84 物理像素（+8.562 DIP）**，字母还大了 3.9 像素。

**产品事实决定了正确语义**：面板存续期间**卡片不会动**（翻牌是原地换内容），
所以整排纵向基准应当在**开边沿定一次、之后复用**；刷新只更新**内容**。

**改法**（两份纯函数，预览与局内共用）：

| 环节 | 函数 | 语义 |
|---|---|---|
| 锁定 | `augment-label.ts` 的 `lockLabelRowBand(prev, cards, zone)` | 已有锁 → **原样返回**（绝不重算）；没锁且这一批卡非空 → 用**这一批**（稳定/冻结）矩形调 `labelRowBand()` 锁一次 |
| 定位 | `augment-label.ts` 的 `alignRowLabelsLocked(cards, lock, zone)` | 纵向取锁定的 `band.y`/`band.h`；横向仍按**各自卡片**水平居中；没有锁 → `[]`（不画） |
| 局内路径 | `augment-tier-label.ts` 的 `augmentTierLabelsLocked(rowLock, cards, tiers, opts)` | 返回 `{ labels, rowLock }`：调用方把上一帧的锁传回来、把新的锁存下去（`debug-augment.ts` 的 `drawTierLabels()`）|
| 无锁形态 | `labelRowBand()` / `alignRowLabels()` / `augmentTierLabels()` | **保留**（单测、离线预览的单排计算、没有跨帧状态的调用方）；语义未变 |

**退化语义（明确定义，别猜）**：

- 面板打开时**一张都没认出来**（这一排没有要画的卡）→ **不锁定**（`null`，输出为空）；
- **首次得到 ≥1 张卡**（无论 1 张还是 3 张）→ 用**这一批**矩形锁定基准；
- 之后**只增不减**：后来多认出来几张 → **沿用同一条基准**（新卡并入这一排，
  不重新成排）；某张认不出（标签消失）→ **基准不动**，剩下的标签**原地不动**；
- 面板**关闭**（或在开边沿重新开一块）→ 调用方把锁丢掉，下一块重新锁。

产物：`report.json` 的 `labels.events[].rowBand` = `{ y, h, lockedAtMs, lockedCards,
justLocked }` —— 一块面板里所有事件的 `y`/`h` 必须**逐位相同**，`justLocked` 只应
在开边沿那一次为 true。终端也会打一行 `📐 整排行基准锁定（3 张卡）：框顶 y=… 框高 h=…`。

单测（`augment-label.test.ts` + `augment-tier-label.test.ts`）：真机那一帧的数字
（卡 1/2 冻结 `y=0.191705 h=0.460611` ↔ 卡 3 动画帧 `y=0.172871 h=0.497603`）下，
刷新前后三张标签的 **y / 框高 / 基线 / cap 高逐位相同（差值 0）**；反向情形
（某张卡矩形 y ±0.03、h ±0.05）同样一动不动；锁定语义（1 张 → 3 张、3 张 → 2 张、
全认不出）不崩且不动；并保留"无锁形态整排对齐"的回归用例。

### 字形数据（矢量轮廓，不是位图）

`packages/vision/src/label-letter-outlines.ts`（生成物）里是 A~Z 的
`contours`：`GraphicsPath.AddString` + `Flatten(0.25)` 出的**闭合多边形**（em 单位）；
填充用**偶奇**规则（与 GDI+ 那条路径的 `FillMode = Alternate` 一致）。
配套的 `packages/vision/src/label-letter.ts`（同一次生成，也是生成物）只有**度量**：

- `advance` / `inkLeft` / `inkRight` / `inkTop` / `inkBottom`（em）；
- `TIER_LETTERS_CAP_RATIO = 0.7002`：平底字母 `H` 的墨迹高/em —— `label-draw.ts` 的
  `LABEL_CAP_RATIO` **引用它**，所以"预览里字号多大、局内就多大"不可能漂。

**为什么拆成两个文件**：渲染端（局内 canvas）只需要**度量**（视觉居中、字距），
而**轮廓**只有离线预览用。合成一个文件会被 `label-draw.ts` 一起拖进渲染端 bundle
（实测 `dist/renderer/overlay-canvas.js` 从 14KB 涨到 74KB；拆开后 18KB，
多出来的 ~4KB 就是 26 个字母的度量）。

**为什么导成矢量而不是点阵**：预览里的字母要按 ~130 帧像素画，
点阵要么存一份 128 行的高分辨率位图（26 个字母 ≈ 300 KB 源码）、要么放大就糊；
轮廓数据全部 26 个字母只有 **1 508 个点 / 34 KB**，而且**任意字号都清晰**。

### 描边与发光：距离场"向外扩"（代替 `strokeText`）

canvas 那边 `strokeText(lineWidth = 2 × reach)` 的几何含义是"墨迹向外扩 `reach`"
（向内那半随后被 `fillText` 盖住）。预览的字形是轮廓，所以：

```
覆盖率 = clamp(1 + reach − 到墨迹的距离)      // +1 含"半像素"修正
```

`reach` 仍由 `label-draw.ts` 的 `tierGlowLayers()` / `letter.outlineWidth` 给 ——
**两边同一份数据**，DPR 或字号变了也不会漂（刻意不用 `shadowBlur`，原因见该文件注释）。

### 两套候选风格（`TIER_TREATMENTS`，用户挑一个）

| 风格 | 深色描边 | 发光 | 发光层 alpha |
|---|---|---|---|
| **A** 细描边 + 弱发光 | 7.0% cap | 16% cap（2 层）| 0.34 / 0.18 |
| **B** 粗描边 + 强发光 | 15.0% cap | 32% cap（3 层）| 0.42 / 0.26 / 0.14 |

**当前上线 = B**（`label-draw.ts` 的 `TIER_TREATMENT`）：对照图里 B 的字母有
明显的深色包边 + 一圈柔光，在花哨的卡面插画上比 A 更容易一眼读出档位。
换风格只改这一行；预览脚本 `--style a|b|both` 可以单独看某一套。

### 视觉居中（展示型字体的墨迹不在前进宽正中）

canvas 的 `textAlign='center'` 居中的是**前进宽**，而展示型字体各字母的墨迹
相对前进宽有偏移（`S` 偏左 0.021 cap、`B` 偏右 0.024 cap…）。所以 `tierTagPlan()`
把 `textX` 修正 `capHeight × centerOffset`（`centerOffset = 前进宽/2 − 墨迹中心`，
逐字母来自实测度量），让**墨迹**正好落在框心 —— 三张卡并排时才不会各自偏一点。
尖括号则按**该字母自己的墨迹宽**排（`inkAspect`），所以每个字母都是"墨迹 + 固定空隙"。

## 十五、面板停留期间的「单卡刷新（reroll）」检测（S5.7，2026-10-06）

### 产品事实（用户 2026-10-06 说明，**按这个理解**）

1. **每一张卡片最多可以刷新一次**（点卡上的刷新按钮，把**这一张**换成另一颗海克斯）；
2. **刷新发生在面板保持打开期间** —— 面板**不会**因为刷新而关闭（所以它也不会
   产生"关→开"边沿）；
3. 因此：**必须在面板停留期间发现"某张卡的内容被换掉了"**，然后

   · 只重认那张卡 → 它的标签**换成新卡的档位**；
   · 新卡**认不出** 或 **该英雄强度表里查不到** → **该卡标签必须消失**；
   · **其余两张不受影响**（它们还是原来那颗，标签不应该闪一下或丢一帧）。

> 为什么这是缺陷而不只是"不够快"：刷新前那次识别出来的字母会**继续贴在已被换掉的
> 卡上** —— 屏幕上显示的是**另一颗海克斯的强度**（错数据），比什么都不显示更糟。
> 用户的原始描述："左右两个海克斯刷新后，标签未更新。"

### 机制：面板打开期间盯"每张卡的画面内容"

```
面板 open 边沿 ──整批识别──> 标签画上屏幕，同时把"那一刻每张卡的指纹"记为**基线**，
   │                          并把**卡片矩形**冻结下来（面板存续期间不再变）
   │
   ├─ 每 REROLL_POLL_MS(400ms) 一帧：按**冻结的取样矩形**算每卡指纹（8×8 / 16×16 灰度格）
   │      │
   │      ├─ 与基线比结构距离 < 阈值 ─→ 这张卡没变（绝大多数帧）
   │      └─ ≥ 阈值 且 本帧"已成形" 且 与上一帧一致（动画已停）
   │              └─→ 判定**这张卡刷新了** → recognize({only:[i]})：**用冻结矩形**裁那一张卡的区域、只 OCR 它
   │                        └─→ mergeRefreshedCards()：只替换这张卡
   │                                └─→ augmentTierLabelsLocked() 重算**整批** → pushLabelOverlay()（整批替换）
   │
   └─ 面板 close 边沿 ──清空标签 + **复位基线/冻结矩形/行基准锁**（绝不跨面板复用）
```

**纯函数**：[`packages/vision/src/augment-reroll.ts`](../packages/vision/src/augment-reroll.ts)
（单测见 `augment-reroll.test.ts`）——指纹、距离、判定、合并都在这里；渲染端只负责"算指纹"（它拿得到画布像素），
主进程只负责"编排"（何时比、何时重认、写日志与产物）。

| 环节 | 在哪 | 说明 |
|---|---|---|
| 指纹计算 | 渲染端 `capture/worker.ts` 每帧 | `augmentCardFingerprint(bmp, rect)`，两区共 320 个格均值（三张卡 < 1ms）；矩形是**冻结**的 |
| 判定 | 主进程 `debug-augment.ts` 的 `maybeDetectReroll` | `rerolledCardIndices({baseline, current, previous})` |
| 只重认变化的那张 | `recognize({ only: [i] })` | 只 `drawImage` **冻结矩形**那一块（≈1.1MB，整帧的 1/18）+ 只跑一次 OCR；本帧检测到的动画帧矩形**只记日志** |
| 合并 + 清标签 | `mergeRefreshedCards()` | 认不出 → `augmentId: null` → 该卡被 `augmentTierLabelsLocked()` 过滤掉（标签消失） |
| 整排几何 | 主进程 `drawTierLabels()` 的 `rowLock` | 行基准**开边沿锁一次**；刷新只改内容，几何不动（§十三 末尾）|
| 推送 | `pushLabelOverlay()` | **整批替换**（渲染端先 `clearRect` 再逐条画）—— 不存在"追加"，也不会留旧字母 |

### 指纹：两区、去掉均值的结构距离

取样区（**卡内**归一化，刻意**不含卡底标签带**）：

| 区 | 范围 | 网格 | 为什么 |
|---|---|---|---|
| `body` | x 0.10~0.90、y 0.06~0.74 | 16×16 | 图标 + 名字 + 稀有度 + 描述全覆盖（描述实测最长到 0.713）；下沿 0.74 **避开标签带** |
| `icon` | x 0.20~0.80、y 0.08~0.36 | 8×8 | 真机标定里**区分度最高**的一区：不同海克斯的图标完全不同 |

距离 = 各区「去掉本区均值后的逐格平均绝对差 ÷ 255」取**最大值**。
去均值让整体亮度变化（技能闪光 / HUD 淡出 / 亮度设置）不参与判定。

> ⚠️ **必须把卡底标签带排除**：覆盖窗画的内容**会进截屏流**（屏幕流拍的就是合成后的
> 桌面），标签画在卡内 y ≈0.79~0.94（最高的一档从上沿 0.788 起）。不排除它，
> 我们自己画上去的字母就会让指纹变化 → 白跑一次"假刷新"。

### 阈值：真机帧标定（`scripts/diag-augment-reroll.mts`）

用两张真机面板帧（`debug/shots/inprogress-152515/152509-raw.png`；它们**卡1/卡2 是同
一颗海克斯、卡3 真的被换过** —— 天然一组"最干净的噪声样本" + 一个"真实的一次单卡刷新"）：

| 组 | 样本 | 距离 |
|---|---|---|
| 噪声（重采样相位 / ±8 灰度噪声 / 5bit 量化 / 3×3 模糊 / 亮度 ±12 / 组合） | 27 | 0.0000 ~ **0.0130** |
| 真变化（把槽位换成另一张真机卡） | 6 | **0.0657** ~ 0.1309 |
| 跨帧同槽位 | 3 | 0.0006（内容相同）/ 0.0069（相同）/ **0.1382**（卡3 真被换过）|

**阈值 `AUGMENT_REROLL_THRESHOLD = 0.03`**：噪声上界的 2.3 倍、真变化下界的 2.2 倍
（脚本的退出码就是这条判据，两边没分开会返回 1）。

#### 2026-10-06 复核：「待机动画被误判成刷新」这条成因**已用真机帧排除**

用户报「局内海克斯面板开着不动、标签几秒后自己消失」。第一个候选成因是
**卡片待机动画让指纹越过阈值 → 触发一次假刷新 → 重认失败 → 按"认不出就清掉该卡标签"
的规则把标签删掉**。用**线上同一份**指纹代码（`augmentCardFingerprint` /
`fingerprintDistance`，两区取最大值）在两帧真机上量过，**不成立**：

取样矩形按**局内真实语义冻结**（两帧都用第一帧定下的那组矩形，等价于 worker 的
`watchRects`），门控画布与线上同一条公式（`gateCanvasWidth(targetScale 1/3, minWidth 960)`
→ 1529×640）：

| 卡 | 内容 | **冻结矩形下的结构距离** | 卡内逐像素 MAE | 判定 |
|---|---|---|---|---|
| 卡1 | 缩小引擎（两帧同一颗，OCR 复核）| **0.0006** | 0.80 / 255 | 没变（阈值的 1/50）|
| 卡2 | 夜狩（两帧同一颗）| **0.0001** | 0.38 / 255 | 没变（阈值的 1/300）|
| 卡3 | 威能之追求 ← **真被换过** | **0.0681**（反向取样 0.1054）| 37.66 / 255 | 真变化（阈值的 2.3 倍）|

（这一组现在由 `scripts/diag-augment-reroll.mts` 直接打印：**"跨帧同槽位 · 冻结矩形"**，
默认底图就是这两帧，退出码会把"同内容最小须 < 阈值、真变化最大须 ≥ 阈值"一起判掉。）

- 两帧相隔 **6 秒**、面板一直开着、**没有任何操作**：卡1/卡2 的像素几乎逐位相同
  （MAE < 1/255）→ 这个界面在那 6 秒里**没有**能被误判的待机动画；
- 卡3 是同一段里**真实发生的一次单卡刷新**：0.0681 ≥ 0.03 ✅ 说明检测本身有效；
- 独立佐证（一局真机录制 `debug/augment/report.json`，2026-10-06）：面板开着
  **26 秒**、69 帧 400ms 采样，**3 次真实刷新全部检出**（0.0537 / 0.0582 / 0.0891
  —— 三张卡各一次，与"每张卡最多刷一次"的产品事实吻合），静态的 7 秒 / 11 秒里
  **一次假刷新都没有**。

**所以不改刷新判定规则**（改它只会把已标定的余量弄没）。这条性质由
`packages/vision/src/augment-reroll.test.ts` 的两组测试锁住：

- **「阈值标定锁」**：真机数字（静态跨帧 0.0069 / 噪声上界 0.013 / 真刷新下界 0.0537 /
  真变化下界 0.0657 / 矩形抖动 0.0311）与余量判据（噪声上界 ×2 ≤ 阈值 ≤ 真刷新下界 ÷1.7）
  一起断言 —— 要动阈值必须先用 `scripts/diag-augment-reroll.mts` 重跑真机帧；
- **行为测试**：同内容不判变 / 内容替换判出 / 未成形中间帧不判 / 画面未稳定不判 /
  「重随重认得到同一个 augmentId」时标签原样。

**"面板没认定 / 卡片数抖动 → 报空指纹跳过该帧"这条保护**（上面第 4 条）已抽成纯函数
`augmentWatchFingerprints()`（`vision/augment-reroll.ts`）+ 单测：它要求"已识别过 **且**
本帧认定面板 **且** 卡片数与冻结矩形数一致"，否则返回空数组。**两个入口共用同一个
`capture/worker.ts`**（录制工具与常驻覆盖层都经 `AugmentController` → `AugmentStream`
拿帧），所以它不可能只在录制工具那条路径上生效 —— 现在这条"跳过"有测试保证，
不再只靠读代码。

三条配套规矩（缺一条就会误判或漏判）：

1. **取样矩形冻结**（渲染端 `watchRects`，面板打开时定下、关闭时清掉）：
   检测每次重建的卡片边线有 **±1~2px** 抖动（内容一变、竖向投影的边线就跟着变），
   拿抖动后的矩形去取样会让"没变"的内容也测出 **0.031** —— 那一项就把噪声顶到阈值上。
   面板停留期间卡片本来就不动，冻结正是对的语义（`diag-augment-reroll.mts`
   把这一组单列为"压力组"并写明局内不会出现）。
   ⚠️ **重随重识别不许重新冻结**（2026-10-06 修）：那时卡片正在翻牌动画里，
   按动画帧的检测矩形重冻会让后续每一帧的指纹都偏 —— 冻结只在**整批识别**（开边沿）做。
2. **"已成形"**：本帧指纹的主区 `std` 低于 `AUGMENT_FINGERPRINT_MIN_STD = 8` 就不判定
   （卡片翻转/淡入的中间帧整块发白或纯色；真机卡片实测 std 15~30）。
3. **画面已稳定**：还要求"本帧与上一帧的差异 < 阈值"。动画中间帧虽然与基线差异很大，
   但它每一帧都在变 —— 加这一条就等到动画停下再判定，**一次刷新只触发一次重识别**
   （代价是多等一个采样周期 ≈400ms，远小于"贴着错字母"的代价）。
4. **只在"冻结矩形仍对得上"时报指纹**：渲染端要求"本帧认定面板 **且** 重建出的卡片数
   与冻结矩形数一致"，否则报空数组、主进程跳过这一帧。面板正在关闭（或卡片数抖动）时
   按旧矩形取样会拿到完全不同的画面，那会变成一次**假刷新**（白跑一次 OCR + 日志里多
   一条假事件）。
5. **重随的裁剪与几何一律用冻结矩形**（2026-10-06 二次验收，见 §十三 末尾）：
   渲染端在开边沿把"这一批识别报告的 `rect`"冻下来（`frozenRects`），重随时
   `recognize({only})` 裁的就是**同一块像素**、回传的也是**同一个矩形**；
   本帧检测到的矩形只用来算差异并记一条日志（
   `卡N 重随：本帧检测矩形与冻结矩形差得明显（Δy … Δh …）→ **仍用冻结矩形**裁剪与定位`），
   **绝不改几何** —— 面板存续期间卡片不动（翻牌是原地换内容），
   拿动画帧矩形改几何就会把整排标签带下去（用户报的那个现象）。

### 采样节奏：只在面板打开时提高（关闭后回到零取帧）

| 时刻 | 采样间隔 | 依据 |
|---|---|---|
| 面板**停留期间** | **`HEXBOX_AUGMENT_REROLL_POLL_MS`（默认 400ms）** | 刷新检测要在这个节奏上比指纹；此时玩家在**做选择**（不在战斗），每帧取像素 ~15ms + 检测 ~2ms |
| 面板关闭后（`api` 模式）| **0 —— 一帧不取** | 触发状态机的常态；刷新检测的基线/冻结矩形同时复位 |
| 面板关闭后（`pixel` 模式）| 节流策略的 `idle` 1000ms / `active` 250ms（tail 20s） | 与接线前完全一致 |

也就是说：**提高采样率只发生在"玩家正在读三张卡"的那几十秒**，常态开销没有变化。

### 为什么"查不到就把该卡的标签清掉"是代码保证的（不是约定）

1. 渲染端重认时 `augmentId` 只能是"认出的 id"或 `null`（`RecognizedCard`，OCR 宁漏勿错）；
2. 主进程 `mergeRefreshedCards()` 把**重认不出**（或结果缺失）的卡置成
   `{ augmentId: null, name: null, ... }` —— 这是**纯函数**，有单测（含"越界序号忽略"、
   "入参不被改"、"别的卡原对象不动"）；
3. `augmentTierLabelsLocked()`（`vision/augment-tier-label.ts`；无锁形态是
   `augmentTierLabels()`）第一道过滤就是
   `augmentId === null → 不画`，第二道是"该英雄表里查不到 tier → 不画"；
4. `drawTierLabels()` 用**整批**重算（几何走**行基准锁**，见 §十三 末尾）+ `pushLabelOverlay()` 整批推送，渲染端
   `clearRect` 后重画 → 脏的那张卡没有输出 = 它的标签消失，其余两张照旧（位置也不动）。

**没有任何"保留旧值/兜底"的分支** —— 那正是用户报的 bug（"比不显示更糟"）。

### 真机怎么看它（产物与日志）

终端一行（每次重随）：

```
[augment] 🔄 检测到卡2 刷新（结构距离 0.081 ≥ 阈值 0.03） → 只重认这几张…
[augment] 🔎 单卡重随重识别 成功（58ms，3440x1440）
[augment] 检测到卡2 刷新 → 重新识别（58ms）→ 卡2 → B（选取率 7.3%）（夜狩）
```

`report.json` 的 `labels` 段：

- `labels.reroll`：`pollMs` / `settleMs` / `threshold` / `detected`（检测到几次）+ `events[]`
  （每次的卡号、结构距离、阈值、轮询间隔）；
- `labels.events[]`：每次（重）识别一条，`origin` = `open`（开边沿整批）/ `reroll`（单卡刷新），
  `refreshed` = 被重认的卡号，`tookMs` = **这次识别的耗时**，`items[]` 给出每张卡最终的
  `tier` / `pickRate` / `drawn`，`rowBand` = **本帧用的整排基准**
  （`{ y, h, lockedAtMs, lockedCards, justLocked }`：一块面板里所有事件的 `y`/`h`
  必须逐位相同，`justLocked` 只在开边沿那一次为 true）。

**验收（真机）**：面板开着点某张卡的刷新 → 终端出现上面三行、屏幕上**只有那一张卡**的
字母变（或消失）；另外两张**不动**；面板关掉后字母全清、且（api 模式）采样回到一帧不取。
`timeline.csv` 的 `cadence` 列会写成 `on@400` / `off`，可核对节奏。

> ⚠️ 与 §七「认不准就不画」一致：**新的那张卡认不出 → 它的标签消失**。这是刻意的
> —— 留着上一颗海克斯的字母属于"显示错数据"。

## 十六、常驻覆盖层接线（S5.4d，2026-10-06）

### 一句话

`pnpm dev:overlay`（常驻覆盖层）现在**自己就会**在局内画海克斯强度标签 ——
它跑的是与录制工具**同一份控制器**（`apps/overlay/src/main/augment-controller.ts`），
不存在第二份触发状态机、第二份刷新编排。

```
LCU 阶段（每 2s 轮询）
   ├─ ChampSelect  → 画布归**选人视觉循环**（vision-loop.ts，1.5s 一轮 + 6 轮 TTL）
   ├─ InProgress / Reconnect
   │      → 画布归**局内海克斯链路**（augment-controller.ts）
   │      → 常态零取帧（api 触发）→ 死亡+等级达标+该次未选 → 开截屏
   │      → 面板开边沿：全分辨率识别 → 该英雄强度表 → 标签（行基准锁）
   │      → 面板停留期间每 400ms 比指纹 → 单卡刷新只重认那一张
   │      → 面板关边沿：**立刻清空**（不复用选人的 6 轮 TTL）
   └─ 其它阶段（大厅/匹配/加载/结算）→ 谁都别画
```

### 1. 抽出的公共控制器（S5.4d 的重点）

| 文件 | 职责 |
|---|---|
| `apps/overlay/src/main/augment-controller.ts`（**新**）| 采集几何、常驻屏幕流（`AugmentStream`）、2999 轮询 + 触发状态机、节流策略、门控边沿 → 识别 → 强度表 → 标签（含**行基准锁**）、单卡刷新编排、计数器/产物行。**不建窗口、不碰样式、不落盘** |
| `apps/overlay/src/debug-augment.ts`（录制工具）| 只用它 + 保留**录制专属**职责：产物（timeline.csv / report.json / checkpoint.json / api-trigger.csv / bench.json）、边沿取证、状态行、阶段等待与跟随整局、Ctrl+C 哨兵、一次性截屏兜底路径、覆盖窗自测、节流自测 |
| `apps/overlay/src/main/index.ts`（常驻覆盖层）| 只用它 + 阶段启停（纯函数）+ 把标签推给**共用**的那块画布（`main/label-overlay.ts`）|

控制器的注入点（两个调用方各自提供）：

```ts
new AugmentController({
  dataDir,                 // data/ 目录（图鉴 + 英雄详情 + 海克斯名字指纹库）
  labels,                  // 标签推送器：push(msg, display) / clear(why) / prepare(display)
  loadData,                // 可选：常驻 overlay 复用已读入的 dataset/builds，免得再读 4.5MB
  trigger: 'api',          // 常驻 overlay 固定 api（常态零取帧）；录制工具沿用环境变量
  inMatch: () => …,        // api 模式只在"确实在对局中"时计 2999 的失败
  onReading,               // 可选：每帧门控读数（录制工具写 CSV/取证；常驻 overlay 不传）
})
```

**为什么必须共用**：这条链路的每一个常数都是真机换来的（判据阈值、指纹阈值、
行基准锁、清空规则、零取帧）。两份实现必然漂移，而漂移的表现是"某一局突然不对"，
排查成本是一整局对局。

### 2. 谁拥有画布（纯函数 + 单测）

`packages/vision/src/visibility.ts`：

```ts
labelProducerFor(stage, panelState, prev, { augmentEnabled }) →
  { producer: 'champ-select' | 'augment' | 'none', shouldDraw, handover }
```

| 阶段 | 生产者 | `shouldDraw` |
|---|---|---|
| `ChampSelect` | `champ-select` | `true`（具体画什么由视觉循环逐轮决定）|
| `InProgress` / `Reconnect` | `augment` | **只看面板是否在屏**（关闭/未知 → 必须为空画布）|
| 其它（大厅/匹配/加载/结算/未知）| `none` | `false` |

- **两个生产者互斥**，由单测锁住：选人阶段 `decideVisible().visionActive === true`
  且 `augmentChainActive() === false`；局内反过来。谁把 `visionActive` 扩到局内，
  或者忘了在选人阶段拦住局内链路，测试立刻红。
- **阶段切换瞬间**（`handover === true`）主进程**复用现成的 `clearLabelOverlay()`**
  清掉对方遗留的标签 —— 真实场景：上一局面板还开着时对局结束，局内字母会一直挂在屏幕上。
  首轮（`prev === null`）不算换手（启动时画布本来就是空的）。
- **面板开/关不算换手**（同一个生产者的事）：清空由局内链路自己在关闭边沿做，
  避免每开一次面板都多推一次清空。
- 启停也是纯函数：`augmentChainTransition()`（局内只起一次、离开立刻停、
  **在途启动按会话令牌作废 —— 且只作废自己那一代**、失败本局不重试）；
  标签生命周期与链路生命周期**解耦**：链路停止**不清标签**（§6）。
- 单测：`packages/vision/src/visibility.test.ts` 数量以 `pnpm test` 为准
  （画布归属 12 项 + 启停状态机 7 项 + 会话令牌 3 项，含"一局完整阶段序列回放"）；
  另有**时间轴回放**回归 `augment-timeline.test.ts`（`scripts/diag-augment-stage-timeline.mts`
  同一份纯函数，`--before` 打印改前对照），锁住"局内阶段稳定读到时 stop = 0"
  与"链路停止不清标签"。

### 3. 降级开关

```powershell
$env:HEXBOX_OVERLAY_AUGMENT='0'; pnpm dev:overlay
```

- **只关局内那一条链路**：选人阶段的胜率标签**照常工作**（两个生产者的判定分开，
  且开关关掉时局内归 `none`，画布换手会把局内遗留清掉）；
- 判定规则：只有显式写 `0` / `false` / `off`（大小写与空白无关）才关掉 ——
  手滑写成 `true`/`1` 不会静默关功能（`overlayAugmentEnabled()`，有单测）；
- 另有 `HEXBOX_AUGMENT_DRAW=0`：链路照跑（识别 + 日志），只是**不画**（与录制工具同语义）；
- 链路自己的旋钮（`HEXBOX_AUGMENT_REROLL_POLL_MS` / `HEXBOX_AUGMENT_BADGE` /
  `HEXBOX_AUGMENT_API_POLL_MS` …）在 `main/augment-controller.ts` 头注里列全了。

### 4. 常态零取帧 + 干净退出

- 常驻 overlay **固定 `api` 触发**：常态 `setCadence(0)`（**一帧不取**），
  只有「死亡 + 等级达标 + 该次未选」才开截屏；面板停留期间 `HEXBOX_AUGMENT_REROLL_POLL_MS`
  （默认 400ms）比指纹，面板一关**立刻回到 0**；
- 进/出对局：`InProgress`/`Reconnect` 起，离开就 `stop()`（停流 + 清标签 + 丢行基准锁与重随基线）；
- **关闭覆盖层**（`before-quit`）会 `stop()` 一次：销毁隐藏的截屏 worker 窗口、
  停掉门控定时器、清空标签与心跳 —— **不留屏幕流、不抢焦点、不留幽灵窗口**；
- 起链路失败（屏幕流没就绪）只记 `failed`，**本局不重试**（避免每 2s 建一次流），
  下一局重新试；日志写明原因。

### 6. 标签生命周期：**谁有权清空**（2026-10-06 二次修正；每一次清空都打印原因）

用户报「面板开着不动、标签几秒后自己消失」时，唯一能回答"是谁清的"的东西就是日志。
所以**每一条清空路径**都改成同一行格式（词表与格式在
`vision/augment-clear.ts`，**有单测锁住字面量**）：

```
🧹 清空强度标签：原因=<词表里的一条>（可选补充）
⏹ 链路停止但不清标签（面板仍开）：原因=<为什么停> —— 标签只由「面板关闭边沿」或「确认离开对局」清空
```

> **规则（勿违）**：局内强度标签的生命周期**只**由
> ① **面板关闭边沿**（门控连续未认定面板）、
> ② **确认离开对局**（阶段门确认 → 画布换手 `clearLabelOverlay()`）、
> ③ 本次（重）识别一个可画标签都没有（隐式清空，底线行为）
> 决定。**链路自己的启停不再是清空来源**（`vision/augment-clear.ts` 的
> `augmentStopClearsLabels()`：默认**不清**；只有"程序退出""录制收工"这类
> **明确要求**才 `{ clearLabels: true }`）。
>
> 为什么（2026-10-06 真机反馈：**"面板刚弹出、标签刚画上，随即被清掉"**）：
> 改前 `AugmentController.stop()` **无条件**清标签，于是链路生命周期（起/停）
> 与标签生命周期绑在一起 —— **任何**一次停止都会把**面板还开着**的标签抹掉；
> 而局内强度标签一局只推一次（面板开边沿），链路一停那块面板就再也画不出标签。
> 真机上最凶的一条是"在途启动被作废"的回调把**期间新起的那一代**连流带标签
> 一起收掉（见 §6.1），它可以在面板刚画上标签的那一秒落地。

| # | 谁清 | 什么条件 | 会不会被**一次偶发失败**触发 |
|---|---|---|---|
| 1 | `AugmentController.clearLabels()`（`原因=面板关闭边沿`）| 门控**连续 N 帧**未认定面板（`createPanelTracker` 的 `closeAfterMisses`）| 单帧抖动**不会**（要连续 N 帧）。真机一局实测 69 帧 open 期 0 次误判；日志写明"第 N 次" |
| 2 | `main/index.ts` 的画布换手 `clearLabelOverlay()`（`原因=阶段换手`）| `labelProducerFor(...).handover`（生产者变了）—— **这是"确认离开对局"的清空路径** | **不会（已修）**：改前 `augment → none` 由**一次**读失败触发；现在喂给它的阶段来自阶段门（读失败保持、离开要连续 2 次确认，§7）|
| 3 | **`AugmentController.stop()` 不再清标签**（改前是"无条件清"，`原因=链路停止`）| 只有在调用方明确要求时才清：**程序退出**（`before-quit`，窗口马上销毁）、**录制收工**（`debug-augment.ts` 的 `finish()`）| 局内任何一次停止（离开对局 / 启动失败 / 在途启动被作废）都**只打印** `⏹ 链路停止但不清标签…`，不动屏幕 |
| 4 | `drawTierLabels()` 推 `active:false`（**隐式清空**，不调 `clear()`）| 本次（重）识别**一个可画标签都没有**：`原因=重识别失败`（开边沿整批）/ `原因=刷新后认不出`（重随整批）| 设计如此（底线行为）。现在**也会打印原因** —— 改前这条在日志里是静默的 |
| 5 | 重随后**单卡**丢标签（`原因=刷新后认不出` / `原因=刷新后查不到强度`）| 那张卡 OCR 认不出，或认出了但**该英雄强度表里没有**它 | 只在真实刷新后发生；两种情形**分开写**（识别问题 vs 数据覆盖问题，排查方向不同）|
| 6 | 选人视觉循环 `VisionLoop.stop()` 推一帧 `active:false` | 离开 `ChampSelect`（`decideVisible().visionActive` 翻转）| 单次阶段抖动**不会**（阶段门挡住）；真离开对局时它清的是**上一局遗留**（同一块画布）|
| 7 | `AugmentStream.unwatch()` | 关闭边沿/收工 | **不清标签**（只丢冻结的取样矩形与基线）|
| 8 | `label-overlay.ts` 的心跳 | 每 1 秒重申置顶 + 重推**最后一次内容** | 只会让标签**更稳**（`active:false` 时停心跳）|

**代价（诚实记录，宁可多留也不要闪一下就没）**：

- 链路因故停掉、而**面板确实还开着**（且阶段还没被门确认离开）时，标签会多留
  **最多一个轮询周期**（`POLL_MS` = 2 秒）到下一次真离开/面板关闭边沿 —— 这是
  刻意选的：清早了是"面板还开着标签没了"（用户报的缺陷），清晚一轮只是字样多留 2 秒。
- 反过来**不会**因此留下永久残留：真离开对局 → 阶段门确认 → 画布换手清空；
  面板真关了 → 关闭边沿清空；程序退出/录制收工 → 明确清空。

#### 6.1 在途启动的作废：**会话令牌**（2026-10-06 真机缺陷的根因）

改前 `applyAugmentChain()` 在 `start()` 的回调里用"看到新世代就 `stop()`"作废在途启动：

```ts
if (gen !== augmentGeneration) { controller.stop('阶段已变化'); return }   // ❌ 改前
```

`AugmentController.start()` 要先探窗口 + 建流 + 等就绪（最长约 10 秒），期间阶段完全
可能"确认离开"又"回到对局"。那条**在途启动**的回调落地时，如果期间已经起了新一代，
这次 `stop()` 会把**新一代**的流一起收掉并清掉它刚画上的标签 —— 真机表现正是
**"面板刚弹出、标签刚画上，随即被清掉"**，日志里看到的是
`🧹 清空强度标签：原因=链路停止`。

现在改成**令牌制**（纯函数在 `vision/visibility.ts`，有单测）：

- `augmentChainTransition()` 除动作/状态外还给出 `token`：`start` = **新会话号**
  （单调递增，绝不重号），`stop` = **要作废的那一代**；
- 控制器 `start(token)` 在每个 await 检查点比对令牌（`isCurrentSession()`），
  不一致就**只收掉自己那代的流**（`dropStream(mine)`，按 `streamToken` 判归属）；
- 回调里只允许 `augmentStartIsStale(token, session)`：过期就**什么都不做** ——
  既不碰新一代的流，也不碰它的标签。因为本代的流已经自行收干净，
  "什么都不做"**不会**留下没人管的屏幕流（这正是上一轮"故意不改"的理由）；
- `stop(why, { token })` 只允许作废**自己那一代**：令牌不符直接忽略（日志会写明）。

**怎么复现/回归（不需要真机）**：

```powershell

node --experimental-strip-types scripts/diag-augment-stage-timeline.mts            # 现行为
node --experimental-strip-types scripts/diag-augment-stage-timeline.mts --before   # 改前（对照）
node --experimental-strip-types scripts/diag-augment-stage-timeline.mts --scenario flash --before
pnpm --filter @hexbox/vision test        # `augment-timeline.test.ts` 里的硬断言
```

回放里的 `flash` 情形就是真机那一刻：冷启动跨 14 个轮询周期 + 启动窗口内读失败风暴
（门连输 → 按离开处理）→ 新一代热启动就绪并画上标签 → 旧一代回调落地。
改前：`stop=3`（**局内阶段上的 stop=1**）+ `🧹 链路停止` 把刚画上的标签清掉；
现行为：过期回调**被忽略**，局内阶段上的 stop=0，标签留到真的离开（`阶段换手`）。

#### 6.2 关闭判定是**两个信号 + 一个复检窗口**（2026-10-06 真机回归：面板还开着，标签却没了）

**症状**：局内海克斯面板开着不动，三个强度标签"出现一瞬间就消失了"，而且那块面板
**再也画不出标签**（用户报告 + `apps/overlay/debug/overlay-augment.log` 真机日志）。

**根因（已用真机数据证实，不是推断）**：**单卡重随（reroll）的翻牌动画**会让
`augment-panel.ts` 的**卡片判据**（结构 + 内部暗 + 边框对比）连续失效约 **1 秒**。
真机时间线（`debug/augment/timeline.csv`，像素模式 400ms 采样）里完整的一段：

| ms | found | cards | bands | state | 说明 |
|---|---|---|---|---|---|
| 32524 | 1 | 3 | 6 | open | 面板正常 |
| 32930 | 0 | 0 | 4 | open | 翻牌开始：卡片判据失效 |
| 33333 | 0 | 0 | 4 | **closed** | ★ 第 2 帧失效 → **旧阈值（2 帧 = 0.8 秒）判"关闭"** |
| 33612 / 33862 | 0 | 0 | 4 | closed | 失效持续 |
| 34108 | 1 | 2 | 8 | ── | ★ **面板其实一直在**（卡片又回来了）|

失效总长 **1178ms**（32930 → 34108），而 400ms × 2 帧只有 0.8 秒 → 必被穿过去。
API 模式下误判关闭还会**停取帧**（`⏱ 采样间隔 → 停（常态零取帧）`）→ 没有帧就
不可能产生新的开边沿；API 那边也没有"死亡 + 等级达标 + 未选"的新事件 → 这块面板
永久空白。真机日志的形状完全一致：

```
[augment] 🔌 关截屏：未见面板即关闭：关截屏，待选 […] 保留
[augment] ⏱ 采样间隔 → 停（常态零取帧）：…
[augment] ◀ 面板消失 #1 @44.0s — 依据：卡片判据连续未命中 2/2 帧；面板信号 0/5 帧仍成立…
[augment] 🧹 清空强度标签：原因=面板关闭边沿（第 1 次）
```

**修法（三层，缺一不可）**：

1. **第二条信号：「面板仍在」**（`vision/augment-presence.ts`，纯函数 + 单测）。
   面板是 UI 覆盖层：三张卡的上/下缘是两条**横贯卡片宽度的亮线**，翻牌是**绕竖轴
   翻转** → 内容在动、上下缘的 y 不变。判据：搜索区上半（y≤0.45）与下半（y≥0.55）
   各有一行亮像素占比 ≥ **0.25**、两行跨度 0.40~0.90、且每条带相对"带外紧邻行"
   突出 ≥ **0.15**（最后一条是**线**判据：整片亮背景不算）。渲染端**只在卡片判据
   未命中的帧上算**（命中帧当然在）→ 常态零额外开销，只有翻牌/真关闭那几帧多一次
   按行扫描。真机标定表见该文件头部（正样本 0.46~0.49 vs 阈值 0.25）。
2. **关闭确认改成"两个信号都不在，连续 3 帧"**（`augment-panel.ts` 的
   `PANEL_CLOSE_CONFIRM_FRAMES = 3`，400ms 采样 = **1.2 秒**，是用户验收过的清空
   延迟上限）。"卡片判据失效"单独一票**不足以**关闭；面板信号托底有额度
   （`PANEL_PRESENCE_TRUST_FRAMES = 5` 帧 ≈ 2 秒），额度用完就不再托底
   —— 这样既不会被 1.2 秒的翻牌穿过，也不会因为信号误报让标签永远不消失。
3. **关闭确认状态机 + 自愈**（`vision/augment-close-confirm.ts`，纯函数 + 单测）。
   门控的关闭边沿**不当场**上报给 API 触发状态机：先进 `AUGMENT_CLOSE_CONFIRM_MS`
   （**3 秒**）的**复检窗口**，窗口内**继续取帧**（`ACTIVE_MS` = 250ms）；
   - 窗口内面板重现（开边沿）→ 那次关闭是**假关闭**：作废，**不消耗待选、不关截屏**，
     日志打 `🔒 假关闭作废（第 N 次）`；开边沿本身会重新识别并重新画出标签（自愈）；
   - 窗口到期仍没见过面板 → 才 `notePanelClosed()`（消耗一次待选 + 关截屏，
     回到原有路径），日志打 `🔒 关闭确认`。

**为什么必须第 3 层**：只把帧数 2→3 是**不够**的 —— 翻牌实测 1178ms vs 1.2 秒，
**余量只有 22ms**（低于一帧的抖动）。第 3 层让"误判"变成可恢复事件：即使门控真的
判错，复检窗口内面板会自己回来。

**代价（诚实记录）**：

- **标签清空时刻不变**：仍然是关闭边沿**立刻**清（1.2 秒内），所以"选完立刻清空"
  这条已验收行为没有变慢；代价是假关闭时标签会先消失、约 0.4~1.2 秒后自愈回来
  （一次短暂闪烁）—— 比"永久空白"好得多。
- **真关闭时"关截屏 / 消耗待选"晚 3 秒**，并多取约 12 帧（250ms × 3 秒、
  1/3 分辨率，一帧约 18ms → 总共约 0.2 秒 CPU）。这是**取帧开销**，不是标签延迟。
- **极端情况**：如果"面板信号"在面板已经关了之后还连续误报，门控最多多留
  `5 + 3 = 8` 帧（约 3.2 秒）标签就会关掉 —— 有硬上限，不会永久残留。
- **已知假阳性**：选人界面（客户端）的英雄卡几何同档，也能让这条信号报"在"。
  局内链路**只在 `InProgress`/`Reconnect` 跑**，选人帧到不了这个判据；即使到了，
  上限仍是上面那 8 帧（详见 `augment-presence.ts` 头部的 ★ 段）。

### 7. 阶段读取失败 ≠ 离开对局（真机缺陷的根因与防护）
**根因（2026-10-06）**：`main/index.ts` 每 2 秒读一次 `/lol-gameflow/v1/session`，
旧实现用 `client.getOrNull()` + `phase = String(s.phase ?? 'None')`，于是**三种结果
被压成同一个 `'None'`**：

| 真实情形 | 旧实现 | 后果 |
|---|---|---|
| 读到会话 | `phase = 会话阶段` | 正常 |
| **确实没有会话**（404/400，大厅里正常）| `'None'` | 正常（本来就该停）|
| **读失败**（5 秒超时 / 网络抖动 / 5xx / 鉴权失效）| `'None'` ❌ | **一次偶发失败 = 两条不可逆清空**：① `labelProducerFor('None', …, 'augment')` → `handover` → 清画布；② `augmentChainTransition('running', gen, 'None')` → `stop` → 控制器再清一次（还丢行基准锁与重随基线）。而且重新起链路时 **API 触发状态机是新的**（`capture=false`）→ 面板还开着也一帧不取 → **那一块面板再也画不出标签** |

**防护**（纯函数 + 单测：`packages/vision/src/visibility.ts` 的 `createStageGate()`）：

1. **读失败不算离开**：`null` 输入（超时/网络抖动/5xx/鉴权失效）**保持**上一阶段；
   只有连续 `AUGMENT_STAGE_READ_FAIL_LIMIT`（默认 **5** 次 ≈ 10 秒）都读不到才认输
   （否则 LCU 真挂了会把标签永远挂在屏幕上）；
2. **离开要连续确认**：读到"不在局内"要连续 `AUGMENT_STAGE_LEAVE_CONFIRM`（默认 **2** 次 ≈ 4 秒）
   才采纳；上一轮本来就不在局内时（大厅→选人这种正常切换）**当轮立即采纳**，
   绝不延迟选人覆盖层；
3. **三态分流**：只有 `404/400` 才被当成"确定的没有会话"（→ `'None'`）；
   `401/403` 丢凭证并算读失败；其它状态码/异常都算读失败；
4. **⚠️ 2026-10-06 补的一条**：**读到了会话、但 `phase` 字段不可用**（缺字段/空串/
   非字符串）→ 归为 **`null`（这一轮不知道）**，**不是** `'None'`。
   判定在纯函数 `stageSampleFromSession()`（有单测；`stage-sample.test.ts`）。
   改前写的是 `String(read.phase ?? 'None')` —— "读到了一个看不懂的会话"被当成
   "已经离开对局"，连续两次就确认离开 → 停链路 + 清整排标签，而面板可能还开着。
   这正是真机日志里"`⚠ 疑似离开对局（第 1/2 次）→ 保持 InProgress`"之后紧跟着
   "`阶段换手（augment → none）` + `链路停止（离开对局）`"看起来自相矛盾的原因之一；
5. 门只做"该不该相信这次读数"，启停与画布归属仍然由 `augmentChainTransition()` /
   `labelProducerFor()` 判定（喂给它们的**必须是门的输出** —— 2026-10-06 复核过：
   `main/index.ts` 里 `phase = gated.stage`，两处用的都是门输出，**没有**用原始读数）；
6. 真离开对局时**照旧清空**（底线不变：错数据绝不留）。

**看什么**：门现在**每一次结论变化都打印**（去重后），包括"第 2 次确认离开"那一轮
—— 改前那一轮是**静默的**，于是日志里看起来像"上一行还在保持 InProgress，下一行
就已经阶段换手清标签"：

```
[hexbox] ⚠ 保持 阶段读取失败（第 1/5 次）→ 保持 InProgress，**不**当作离开对局（否则一次超时就会清掉整排标签）
[hexbox] ⚠ 保持 疑似离开对局（读到 None，第 1/2 次）→ 保持 InProgress
[hexbox] ✔ 采纳（离开对局） 连续 2 次读到 None → 确认离开对局     ← 改前这一行**不存在**
```

| `原因=面板关闭边沿` | 门控**两个信号都认定面板不在**、连续 3 帧（400ms 采样 = 1.2 秒）| 看同一时刻的 `◀ 面板消失 #N — 依据：…`（它会打出卡片判据未命中几帧、面板信号托底几帧、阈值各是多少）。若**是**翻牌被误判，紧接着会出现 `🛡 面板信号托底` 或 `🔒 假关闭作废（第 N 次）` —— 那说明自愈生效（面板回来了）|
| `🔒 假关闭作废（第 N 次）` | 关闭边沿之后、复检窗口（3 秒）内面板**又出现**了 → 上一次关闭是误判 | **这是好消息**：待选没被消耗、截屏没关，开边沿会重新识别并重新画标签。若这条频繁出现，说明翻牌时长/门控判据需要复标定（拿 `debug/augment/timeline.csv` 的 `presence`/`presenceHolds` 列看）|
| `🛡 面板信号托底` | 卡片判据失效但"面板仍在"信号成立（翻牌动画的典型形状）| 正常抖动。次数超过 5 帧（托底额度）会失效并开始计入未命中 —— 日志会在关闭依据里写明"面板信号已用完托底额度"|
| `⏹ 链路停止但不清标签（面板仍开）` | 链路停了，但标签**故意保留**（标签只由面板关闭边沿/确认离开清空）| 看 `原因=` 后面那一项：`离开对局` = 阶段被确认离开（看它上面的 `⚠ 保持 疑似离开对局` / `✔ 采纳（离开对局）` 两行）；`屏幕流不可用`/`启动异常` = 本局链路没起来。**标签不会因为这一行消失** |
| `原因=链路停止` | 只有**明确要求**时才出现（程序退出 / 录制收工）| 出现它说明是退出路径或录制工具收工，不是局内故障 |
| `原因=阶段换手` | 画布生产者变了（augment ⇄ champ-select ⇄ none）—— **这是"确认离开对局"的清空路径** | 看 `[hexbox] 进入对局` / 阶段行；真换手（进选人/回大厅）时这是**正确**的清空 |
| `原因=刷新后认不出（卡N）` | 重随之后那张卡 OCR 认不出 | 看 `🔄 检测到卡N 刷新（结构距离 …）` 与 `🔎 单卡重随重识别`：距离只要 ≥0.03 就是**真的换了内容**；若距离很大但画面没变，属识别问题（分辨率/字体 → 复标定 `diag-augment-name-ocr.mts`）|
| `原因=刷新后查不到强度（卡N）` | 认出来了，但**该英雄的强度表里没有**这颗 | 正常（官方每英雄只有 95~162 条；37 颗海克斯没有任何官方强度）—— 标签消失是**已验收**的底线行为 |
| `原因=重识别失败` | 开边沿整批没有可画结果（认不出 / 没认出英雄）| 看 `本局英雄 …（来源 …）`：`none` = 一张都没画 |

若"面板刚弹出、标签刚画上，随即被清掉"，先看两处（不要猜）：

1. `grep '🧹 清空强度标签'` —— 有 `原因=阶段换手` 说明**阶段被确认离开**了
   （看它上面的 `⚠ 疑似离开对局` / `阶段读取失败`）；
2. `grep '⏹ 链路停止但不清标签'` 与 `grep '忽略已作废的启动结果'` —— 有它们说明
   那次停止**没有**动标签，问题在别处（渲染端/窗口层，或面板关闭边沿被翻牌动画打掉）。

若日志里**一条 `🧹 清空强度标签` 都没有**而标签确实消失了 → 说明是**渲染端/窗口**层
的问题（画布被清空但没有主进程清空动作），改用 `HEXBOX_LABEL_OVERLAY_TEST=1` 先验窗口，
并把 `debug/overlay-augment.log` 全文发回。



## 十七、2026-10-11 真机修复批次（记账 / 频率 / 误判 / 多实例）

这一节记录**同一天**从两份真机日志（打包版 `%LOCALAPPDATA%\hexbox\logs\overlay.log`）
里定性的五件事，以及它们的修法与回退点。**每一条都先有日志证据再改代码。**

### 1. api 模式的采样频率：面板状态**优先于**触发状态机（纯函数）

`apiTrigger` 的记账一旦偏位（下一节），就会出现"面板明明开着，API 却说
`capture=false`" —— 此时如果按触发状态机把间隔压回 `0`，就是**一帧不取**：
面板上的标签永远不更新、也永远关不掉。

所以"下一段采样间隔"抽成纯函数 `apiCaptureInterval()`
（`packages/vision/src/augment-cadence.ts`，有单测），顺序写死：

| 优先级 | 条件 | 间隔 |
|---|---|---|
| 1 | **面板在屏**（`state === 'open'`）| `HEXBOX_AUGMENT_REROLL_POLL_MS`（默认 400ms）|
| 2 | 触发状态机在开截屏 | `HEXBOX_AUGMENT_ACTIVE_MS`（250ms）|
| 3 | 关闭待确认的复检窗口 | 同上（没有帧就不可能有开边沿，自愈无从谈起）|
| 4 | 其余 | **0 —— 一帧不取**（严格常态零取帧）|

#### 关后自愈探针：**默认关闭**（用户裁决）

`augment-close-confirm.ts` 的头注写明过一个死锁：api 模式"确认关闭"之后间隔是 0，
**若面板其实还开着**（误判关闭）→ 没有帧 → 没有开边沿 → 永远无法自愈。
录制工具默认 `pixel` 模式帧永不停，所以同一个误判在录制里能自愈、在常驻路径不能。

第 4 条分支留了一个**低频自愈探针**：确认关闭后的 20 秒（`TAIL_MS`）内以
6 秒（`PROBE_MS`）采一帧，窗口过后回 `0`。代价与收益是**产品取舍**：

- 打开：误判后最多 6 秒自愈；代价 = 关闭后 20 秒内 1 帧/6 秒；
- 关闭：**严格零取帧**（用户 2026-10-11 的选择）；误判关闭后仍然无帧可自愈，
  靠上面第 2 节（记账）与第 3 节（幽灵标签）**降低误判概率**。

回退点只有一个常量：`apps/overlay/src/main/augment-controller.ts` 的
`CLOSE_HEAL_PROBE`（环境变量 `HEXBOX_AUGMENT_CLOSE_HEAL_PROBE=1` 可临时打开）。
两种状态都有单测（`augment-cadence.test.ts`）。

### 2. 开局窗口内**不许重复** `startCapture()`（记账错位的根因）

`augment-trigger.ts` 的开局分支原来是"只要对局 ≤25s 且开局那次没选就
`startCapture()`"，而 `startCapture()` 里有一句 `sawPanel = false`，
API 又是每 1 秒轮询一次 → 门控刚 `notePanelOpen()` 置上的"见过面板"
**下一秒就被抹掉**，关边沿于是走 `wasSaw === false` 分支，日志出现自相矛盾的

```
▶ 面板出现 #1      ← 明明见过面板
🔌 关截屏：未见面板即关闭   ← 却说没见过
```

而且 25 秒内采样间隔在 0/250ms 之间反复跳（capture 被反复"重新打开"）。

**修法**：`if (!capture) startCapture(...)` —— 已经在开截屏就一个字都不改
（不清 `sawPanel`、不推窗口、不重复报"开截屏"）。
另外把 `notePanelClosed()` 在"当时没在开截屏"这条路径上的 `reason` 改成
如实描述"已经消耗了一次"（原来沿用了上一次的字符串，会打出"看起来没消耗"的假日志）。
两条都有单测（`augment-trigger.test.ts` 的"开局窗口"段）。

### 3. 幽灵标签：`label-memory` 的**容量上限** + `vision-loop` 的**阶段重置**

真机日志（L34 → L40）的原始形状：

```
L34 推送 active=true labels=1 … 第一阶段: 卡片 2 张 → 出标签 1 个 … 标签0@(1160,621)
L40 推送 active=true labels=4 … 第一阶段: 卡片 3 张 → 出标签 3 个 … 标签0@(757,614)
L41~L78 draw labels=4（约 20~25 秒）→ L79 才回到 3
```

`label-memory.ts` 的"按位置记忆"只比 x/y（容差 24 DIP、TTL 6 轮）：
某个误检轮产出的标签 @(1160,621) 与下一轮三个正确标签**两两都差 >24 DIP** →
位置规则认不出它是同一个元素 → **原样保留** → 屏幕上 4 个（3 个正确 + 1 个带旧英雄名的幽灵）。

**修法**：记忆里记"本块 UI 见过的最大元素数" `capacity`（`reset()` 清 0，
每轮用本轮输入条目数取 max），合并输出时 `out.length >= capacity` 就停手。
语义两条都要保住：3 张某轮只检出 2 张仍能补齐第 3 个；而"误检成 2 张后再检出 3 张"
时容量升到 3、3 个新标签已经占满 → 幽灵永远进不来。

第二条（同一天 L86）：

```
推送 active=true labels=3 … 第二阶段(locked): 顶栏占用 2 格, 识别成功 0 格
```

二阶段那一轮产出 0 个，却仍在推 3 个**卡片**标签 —— 它们靠 TTL 挂着。
根因是"换阶段清记忆"只看 LCU 的 `pickState`，而 `pickState` 可以是
`unknown`/`picking` 却因为**顶栏占用 > 0** 进二阶段（`isPhase2` 的另一半），
那条路径下 `pickState` 从来不变 → 重置**永不触发**。

**修法**（`main/vision-loop.ts`）：① `pickState` 每 tick **只读一次**并传进
`runVisionRound()`（原来 tick 读一次、`runVisionRound` 又读一次，中间隔着 1~2 秒的
截屏 await，LCU 每 2 秒轮询足以把 picking 翻成 locked）；
② 换阶段判据改成"**实际阶段**变化"（`runVisionRound` 回报 `stage: 'cards' | 'topbar'`），
`pickState` 那条保留作补充。

**验证**（`node --experimental-strip-types debug/diag-ghost-label.mts`，真机帧 + 线上记忆）：

| 场景 | 改前 | 改后 |
|---|---|---|
| 全真机帧 `real/shot1.png`（只重建出 2 张卡 → 2 个标签）→ `champselect-locked-152419`（2 个正确标签，整排偏 33 DIP）| **4** | 2（容量上限）|
| 真机日志 L34 的标签 @(1160,621) → 真机 3 卡帧的 3 个标签 | **4** | **3**（容量上限）|
| `real/phase1.png`（一阶段 2 个）→ `real/phase2.png`（二阶段 1 个，`pickState` 读不到）| 3 | 1（阶段重置）|

### 4. 单卡刷新：第一次没查出强度**先重认一次**；基线**不许倒退**

真机日志（同一张卡、同一个结构距离 0.0735 出现两次）：

```
检测到卡2 刷新（0.0735）→ 重新识别（12ms）→ 卡2 → 不画（查不到强度）
🧹 清空强度标签：原因=刷新后查不到强度（卡2）
检测到卡2 刷新（0.0735）→ 重新识别（12ms）→ 卡2 → S（选取率 11.2%）
```

两次 OCR 拿到的名字与分数**完全一样**（0.598 / 0.082）—— 差别只在"这一次查表查不到"。
所以：

1. **第一次失败不清**：`vision/augment-reroll-retry.ts` 的 `decideRerollRetry()`
   （纯函数 + 单测）给每张卡**一次**重试额度 —— 先保住上一帧的标签，
   在**下一帧**（渲染端只在"面板认定 + 卡片数一致"的帧上报指纹，即"画面已稳定"）
   用 `recognize({ only })` 再认一次；
2. **第二次仍失败必须清**（底线）：`drop` → `mergeRefreshedCards()` 把
   `augmentId` 置 null → 那张卡的标签必然消失（单测锁住）；
3. **基线单调保护**：判定"变了"的那一刻基线已经推进到**检测帧**（新内容），
   而重认报告回传的是渲染端"最近一帧门控画面"的指纹 —— 若它恰好是**变化之前**
   那一帧，基线就被倒回旧内容 → 同一次刷新被重复检出。判据是纯函数
   `shouldAdoptReportedBaseline()`（`reported` 到检测帧的距离 ≤ 到旧基线的距离才采信），
   拒绝时会打一行 `♻ 重认回传的指纹比检测帧更旧 … → 不采信`。

> ⚠️ 如实记录：日志里那对"同一距离出现两次"**最可能的解释是当时的日志文件被
> 两个实例同时写入**（见 §5），即两次检出各来自一个实例；上面的 1/3 两条是
> **把不变量写成代码与单测**（防止基线被回退、防止一次失败就闪标签），
> 不是"已证明的单一根因"。

### 5. ★ 日志里"两套并发的面板会话"：证据指向**多实例**（不是单进程双链路）

第二局的日志里同一个编号出现两次、时间基相差约 1 秒：

```
L574 进入对局（InProgress）→ 启动局内海克斯链路      ← 第 1 次
L582 · worker ready                                  ← 第 1 个 worker 窗口
L585 ✔ 采纳 在对局中（InProgress）                    ← **同一句又打了一次**
L587 进入对局（InProgress）→ 启动局内海克斯链路      ← 第 2 次
L601 · worker ready                                  ← 第 2 个 worker 窗口
L619 ▶ 面板出现 #1 @9.1s
L634 ▶ 面板出现 #1 @8.1s      ← 同一个 #1、时间基差 1 秒
L822 📐 整排行基准解锁（3 张卡，锁定于 9211ms）
L828 📐 整排行基准解锁（3 张卡，锁定于 8204ms）
```

**代码侧判定：单进程内不可能出现上面这个形状。**

- `main/index.ts` 的 `ensureAugmentController()` 是**进程级单例**
  （`if (augment) return augment`，全仓库没有把 `augment` 置回 null 的地方）→
  一个进程只有一个 `AugmentController`，也就只有**一个** `openCount`/`closeCount`/
  `closeConfirm`/`rowLockAtMs`。两个 `#1`、两个 `确认为 1 次的假关闭作废`、
  两个相差 1 秒的 `rowLockAtMs` 只能来自**两个控制器**。
- `[hexbox] ✔ 采纳 在对局中（InProgress）` 这句由**阶段门**打印，门的去重条件保证
  "同一个结论不会连打两次"；两行之间没有任何`⚠ 保持/离开对局`的结论变化 →
  一个进程的同一个门打不出第二行。
- `AugmentStream`（隐藏窗口 + 屏幕流）只由 `AugmentController.startStream()` 创建，
  每个控制器一条；两次 `· worker ready` + `· 屏幕流已建立` + `常驻流已就绪` +
  `⚠ 4 秒内没有收到任何帧` 都出现了两次 → 两个 worker 窗口、两条屏幕流。
- 两条链路算出的**强度表还不一样**（同一排的 火狐/海克斯科技龙魂/吵闹鬼 →
  `B 0.7% / A 1.9% / C 0.3%` vs `C 0.2% / B 0.9% / B 0.9%`）—— 一个控制器在同一秒里
  不可能有两张表；这正是"上一个实例残留、本局英雄没重新解析"的形状。

**结论与用户侧确认**：证据指向**多个 `hexbox.exe` 实例**（打包版是
`requireAdministrator`，残留实例很常见）同时挂在 LCU/2999 上、同时开覆盖画布 →
屏幕上就是"多套标签与胜率重叠"。系统侧确认（任选一条）：

```powershell
Get-Process hexbox | Select-Object Id, StartTime, Path
Get-CimInstance Win32_Process -Filter "Name='hexbox.exe'" | Select-Object ProcessId, CreationDate, CommandLine
```

**可判定的日志特征**（一局内各应恰好出现 1 次；出现 2 次就是多实例）：

```
进入对局（InProgress）→ 启动局内海克斯链路
· worker ready
· 门控已就绪（不取帧）
常驻流已就绪（api 模式…
局内海克斯链路已就绪
▶ 面板出现 #1（对同一块面板）
```

> ⚠️ 本次**不改** `main/index.ts`（另一名 agent 正在改它），所以没有加
> `app.requestSingleInstanceLock()`。**建议的后续动作**：在 `main/index.ts` 的开头加
> 单实例锁（第二次启动直接 `app.quit()` 并把旧窗口前置）—— 这是唯一能根治
> "多实例两套标签"的修法，属于该文件的改动范围。

### 6. presence 判据的 1 帧滞后（不算放宽阈值）

`augment-presence.ts` 头注原来的"只剩两张卡仍过（×1.2 余量）"**只对行占比成立**：
抹掉一整张卡时**亮线突出量**会掉到 0.131 / 0.098（阈值 0.15）→ 整帧判"不在"。

**没有**放宽 `minLineProminence`（那条正是拒绝"整片亮画面"误报的），而是加了
**滞后**：`augment-panel.ts` 的 `PANEL_PRESENCE_HYSTERESIS_FRAMES`（默认 1）——
"上一帧确实在（卡片判据命中或面板信号成立）+ 本帧只是**临界失败**
（占比 ≥0.8×阈值、突出量 ≥0.6×阈值、跨度与位置仍在区间内）"→ 这一帧不算未命中。
代价明确：真关闭最多晚 1 帧（400ms 采样 = +0.4 秒）；"整片亮画面"（突出量≈0）**永远不被放过**。
单测覆盖：临界帧不产生关闭边沿、"presence 连续不在 ≥3 帧仍出边沿"、
额度只有 1 帧、上一帧说不在时不许放过、`presence=null`（旧渲染端）行为不变。

### 7. 常驻路径的轻量诊断（无行为变化）

常驻路径没有录制工具那套逐帧 CSV，所以"重随检测为什么不工作"以前**无法从日志区分**。
现在补了三行（都不改变行为、不落盘）：

- `⏱ 采样间隔 → 停（常态零取帧）：…［capture=… state=… rechecking=…］`
  —— 三个入参一起打，回答"凭什么停"；
- `🧭 面板停留期间 N 帧没有可比指纹（watchRects 未登记/卡数不一致）→ 重随检测不工作`
  —— 每块面板只打一行（在又拿到可比指纹时、或面板关闭时）；
- `◀ 面板消失 #N — 依据：… 面板信号=不在；读数：上 y0.148(0.70，突0.61) / 下 … 跨度0.74`
  —— presence 的**读数**（占比/突出量/跨度）也带上，能看出余量还剩多少。
